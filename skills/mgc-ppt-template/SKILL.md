# 메가MGC커피 PPT 제작 표준 (v4.2, 2026-10-26)

`.pptx` 생성 기술(PptxGenJS 사용법, hex 규칙, validate 절차)은 기본 `pptx` 스킬(`/mnt/skills/public/pptx/SKILL.md`)을 따른다. 이 스킬은 그 위에 메가MGC커피 고유의 브랜드·레이아웃·문구 규칙을 얹는다. 콘텐츠 확보가 끝난 뒤 적용한다.

## 0. 재현 원칙 — 가장 먼저 읽을 것

0. **장르부터 고른다(v3.5, v3.8 개정).** 화면이 많은 기획서·화면 흐름 정의서·요구사항 정의서·통합 기획서(10장 이상)는 **4-C 간결 기획서형**이 기본이다. 중간 보고도 개발 과제의 분기·처리 순서를 보여 주는 보고(흐름도 중심)는 4-C로 만들고, 4-C-8 흐름도 부품과 4-C-5의 중간 보고 장 순서를 쓴다. 화면 캡처 위주로 3단계 이하 기능을 소개하는 짧은 보고(6장 안팎, 패턴 A~F로 다 그려지는 경우)만 4-B 기능 보고형을 쓴다. 애매하면 4-C.
   - 4-B 패턴 A~F에 없는 장(흐름도 등)이 하나라도 필요하면 4-B가 아니다. 4-B 덱에 손으로 그린 장을 섞지 않는다.

1. **기능 보고형은 `scripts/mgc_report.js`를 그대로 써서 만든다.** 좌표·색·글자 크기를 새로 작성하지 않는다. 문구·이미지·패턴 선택만 함수 인자로 넣는다.
   - 스킬 폴더는 읽기 전용이다. `scripts/` 전체를 작업 폴더로 복사한 뒤 쓴다: `cp <스킬 폴더>/scripts/* /home/claude/`
   - `mgc_report.js`는 고치지 않는다. 기준 덱을 실측한 값이라, 고치면 덱마다 레이아웃이 달라지고 `compare_layout.py` 비교가 무의미해진다. 부품이 부족하면 임의로 고치지 말고 사용자에게 패턴 추가를 제안한다.
2. **본문은 4-B-4의 패턴 A~F 중에서만 고른다.** 각 패턴의 호출값(y·h·gap 등)은 표에 적힌 값을 그대로 쓴다.
3. **재현 검증 결과(2026-10-02)**: 기준 개선본 6장을 `scripts/example_interim_report.js`로 다시 만들었다. 도형 216개 중 215개가 좌표·색·글자 서식에서 일치했다.
   - 다른 1개는 의도적으로 고친 것이다. 6장 각주 폭을 12.33에서 9.0으로 줄여, 오른쪽 아래 쪽 번호와 겹치지 않게 했다.
4. 제작 후 7장의 검수 절차를 모두 수행한다. 글꼴·줄 탈락·문장 줄바꿈은 `scripts/check_text.py`가, 장식·화면 밖 요소는 `scripts/check_clean.py`가 검사한다. 기준 덱이 있으면 `scripts/compare_layout.py`로 좌표를 비교한다.
5. **최종본(사용자에게 넘기는 파일)은 4-C-6 최종본 산출물 규격을 따른다(v3.7).** 버전 표기, 작업 이력 제거, 정합성 대조, 산출물 세트 구성이 여기 있다.
6. **개발사 · 연동사와 함께 보는 연동 문서(API · 처리 흐름 · 예외가 들어가는 통합본 · 정의서)는 4-C-9 · 4-C-11을 따른다(v4.0).** 번호 체계 원본 장, 출처 줄, 키(한글 이름) 표기, 개발 구분 값, 쓰지 않는 기능 제거 규칙이 여기 있다.
7. **사용자가 다듬은 pptx를 받으면 다시 생성하지 않고 그 파일을 직접 고친다(4-C-10, `scripts/pptx_edit.py`).** 장을 넣거나 빼면 쪽 번호 · 목차 · 간지 · 본문 장 참조를 모두 다시 맞춘다.
8. **문체 · 기호 · 줄바꿈 · 강조 · 보고 구조는 4-C-12를 따른다(v4.2, 모든 장르).** 제목은 「토픽: 서술」 개조식, 표 칸 · 설명 · 각주는 개조식, 정보 단위 글머리는 「- 」(1개여도), 빈 칸 「—」은 가운데, 강조 빨강은 #FF0000.

## 1. 공통 기본 설정

- `pres.layout = 'LAYOUT_WIDE'`(13.333 × 7.5in)를 슬라이드 추가 전에 명시한다. 언어는 한국어로 한다.
- 폰트는 전부 **맑은고딕(Malgun Gothic)**으로 고정한다. Calibri, Cambria, Pretendard, Inter, 모노스페이스는 금지한다.
  - 글자마다 `fontFace: 'Malgun Gothic'`을 지정한다. 표 셀과 한 글상자 안의 부분 서식도 빠뜨리지 않는다.
  - 테마 글꼴도 맑은고딕으로 바꾼다: `pres.theme = { headFontFace: 'Malgun Gothic', bodyFontFace: 'Malgun Gothic' }`. 기본 테마는 Calibri라서, 바꾸지 않으면 받은 사람이 PowerPoint에서 새 글상자를 추가할 때 Calibri가 들어간다. `mgc_report.js`는 이미 적용돼 있고, 안내문형처럼 직접 작성하는 덱은 이 줄을 넣는다.
  - 검사: `python3 check_text.py out.pptx`가 테마와 모든 글자의 글꼴을 확인한다. 맑은고딕이 아닌 글자가 있으면 위치와 함께 출력한다.
- 여백은 좌우 0.5in, 본문 폭은 12.33in로 한다. 본문은 6.85in 안에서 끝낸다. 하단 정보줄은 y 6.95in에 둔다.
- 렌더 검수(LibreOffice)에서는 맑은고딕이 Noto Sans CJK로 대체된다. 그래서 글자 폭이 실제보다 넓게 보여 줄이 넘어간 것처럼 보일 수 있다. 줄 탈락 여부는 렌더가 아니라 `check_text.py` 결과로 판단한다.
- 금지 요소: 그라데이션, 반투명 블러, 깜박임, 이모지, 같은 모양 둥근 카드 반복, 크림·오프화이트 배경.

### 1-1. 깔끔한 장표 원칙 (v3.1, 사용자 지시)

- **장식 도형은 넣지 않는다.** 화면 밖까지 이어지는 큰 원, 반원, 띠, 사선, 배경 무늬, 장식용 아이콘이 모두 해당한다. 표지도 예외가 아니다.
- **슬라이드 밖으로 나가거나 걸치는 요소는 하나도 두지 않는다.** 모든 도형과 이미지는 0 ≤ x, y이고 x + w ≤ 13.333, y + h ≤ 7.5 안에 있어야 한다.
- **허용하는 도형은 정보를 담는 것뿐이다.**
  - 흐름 헤더 단계
  - 장 구분 칩
  - 내용 박스·카드(텍스트가 들어감)
  - 순번 원(지름 0.4in, 숫자가 들어감)
  - 화살표 글자 "→"
  - 표
  - 화면 이미지와 그 테두리
  - (4-C) 핵심 한 줄의 세로선, 간지 구분선, 화면 구조 장의 영역 테두리와 번호 원(지름 0.24in)
  - (4-C 흐름도, v3.8) 시작·끝 둥근 상자, 처리 상자, 판단 마름모, 안내 상자, 직교 연결선(끝 화살표), 분기 이름 글자, 장 오른쪽 위 범례(모양 4종 + 이름). 모두 4-C-8 부품으로만 그린다
- 도형 하나하나에 대해 "이 도형이 무슨 정보를 전달하는가"를 한 줄로 설명할 수 있어야 한다. 설명할 수 없으면 뺀다.
- 표지는 `addCover()`(`mgc_report.js`)만 쓴다. 단색 배경(doc-bg-800)에 글자 4줄(문서 종류, 제목, 부제, 날짜·부서)만 둔다.
- 검사: `python3 check_clean.py out.pptx` 결과가 '깨끗함'이어야 한다.

### 1-2. 줄 탈락 방지 · 문장 단위 줄바꿈 (v3.4, 사용자 지시)

1. **줄 탈락 금지**: 상자·표 칸 폭이 모자라 글자가 다음 줄로 밀려 내려가는 일이 하나도 없게 한다.
   - 예: "앱카드 관리 진입 위치(핏콜라보 페이" / "지)" → "앱카드 관리 진입 위치(핏콜라보 페이지)" 한 줄.
   - PowerPoint 자동 줄바꿈에 맡기지 않는다. 모든 줄바꿈은 직접 넣은 `\n` 위치(문장 끝, 의미 단위)에서만 생긴다.
   - 여러 줄 칸(카드 설명, 순번 설명, 흐름 박스, 표 칸)도 줄마다 칸 폭 안에 들어가게 의미 단위로 직접 나눈다.
2. **넘칠 때 고치는 순서**
   1. 너비·높이 조절: 인자로 폭을 받는 요소(`label` w, `capture` w, 표 colW·rowH, `kvList` labelW, 직접 그리는 상자)는 주변 요소와 겹치지 않는 범위에서 넓히거나 높인다. 패턴 A~F의 고정 좌표는 바꾸지 않는다.
   2. 문장 축약·줄 나누기: 뜻을 유지한 채 조사·중복어를 줄이거나, 여러 줄 칸이면 의미 단위로 줄을 나눈다.
   3. 자간: `fit_text.js`가 최대 -0.5pt까지 자동으로 좁힌다.
   4. 글자 크기는 3장 타이포 스케일 고정이므로 줄이지 않는다.
3. **문장 끝 줄바꿈**: 서술형·개조식 모두 문장이 끝나 온점(.)이 찍히면 줄을 바꾸고, 다음 문장·항목은 다음 줄에서 시작한다.
   - `fit_text.js`가 생성할 때 자동으로 줄을 바꾼다. 한 줄 칸(제목, 목적 문구, 진행 현황, 캡션, 각주)에 두 문장을 넣으면 줄 수 초과로 생성이 멈추므로, 한 문장으로 합치거나 쉼표로 잇는다.
   - 숫자(1.5), 약어(B.O), 날짜(2026.10.15), 파일명·URL의 점은 해당하지 않는다.
4. **강제 방식**
   - 생성: `mgc_report.js`의 모든 글상자·표 칸이 `fit()`을 거친다. 넘침이 자간 -0.5pt로도 해결되지 않으면 장 역할·문구·초과 글자 수를 담은 오류로 멈춘다. 오류 메시지대로 고친 뒤 다시 생성한다.
   - 검사: `python3 check_text.py out.pptx` 결과가 '글꼴·줄바꿈 통과'여야 한다. 직접 그린 도형과 손으로 고친 파일도 같은 기준으로 잡는다.
   - 글자 폭은 맑은고딕 추정값(한글 0.96em, 굵게 0.98em, 3% 여유)이다. [추정] 실제보다 약간 넓게 잡은 값이라 경계에서는 더 짧게 쓰게 된다.


### 1-3. 정렬 · 가독성 (v3.8, 사용자 지시 2026-10-20)

기준: 「신규 오픈 매장 프로모션 고도화 중간 보고」 개요 장 사용자 수정본.

1. **영역별 콘텐츠 좌우 끝선 일치**: 한 장 안의 표 · 흐름 박스 줄 · 핵심 한 줄 · 캡처는 왼쪽 시작(4-C 0.6in)과 오른쪽 끝(4-C 12.73in)을 같게 맞춘다. 칸 몇 개짜리 줄은 첫 칸 왼쪽 = 0.6, 끝 칸 오른쪽 = 12.73으로 두고 사이 간격을 균등하게 나눈다(칸 시작 간격 = (12.13 − 칸 폭) / (칸 수 − 1), 4칸 · 폭 2.56이면 시작 간격 3.19 · 칸 사이 0.63).
   - 범례 · 보조 설명 · 오른쪽 열 글상자도 오른쪽 끝이 12.73을 넘지 않게 오른쪽 기준으로 계산해 둔다. 왼쪽에서 폭을 더해 가다 끝선을 넘기는 배치는 금지.
   - 표의 열 폭 합 = 본문 폭(12.13)으로 맞추고, 정보가 적은 열(진행 현황 등)은 빼서 남은 열에 폭을 나눈다.
2. **글자 크기 확대**: 여백이 남는 장은 글자를 키워 채운다(줄이지 않음). 검증값:
   - 개요 장 단계 연결 박스: 14pt, 첫머리 'n단계:'만 굵게(나머지 보통), 마지막 결과 칸(다크)은 14pt 굵게
   - 개요 장 핵심 한 줄: 18pt / 일반 장 핵심 한 줄: 15pt
   - 흐름도 상자: 11pt(판단 마름모 굵게), 분기 이름 10pt 굵게, 보조 설명 11pt
   - 넘치면 1-2 순서(폭 → 문장 → 자간)로 고치고, 글자 크기는 위 값 아래로 내리지 않는다.

### 1-4. 정보 덩어리별 글머리 구분 (v3.8, v4.2 개정: 「- 」 고정)

- 보조 설명 글상자 · 표 칸 · 노트 상자에 서로 다른 정보가 2개 이상이면, 정보마다 줄을 나누고 줄 앞에 `- `(하이픈 + 공백)를 붙인다. 표 설명 열은 정보가 1개여도 「- 」로 시작한다(v4.2, 사용자 지시). 「•」는 쓰지 않는다.
  - (×) "종료일은 최대 생성일 + 60일까지, 체크를 해제하면 즉시 미노출"
  - (○) "- 종료일은 최대 생성일 + 60일까지" / "- 체크를 해제하면 즉시 미노출"
- 한 정보가 두 줄 이상이면 이어지는 줄은 글머리 폭만큼 문단 들여쓰기(marL)로 맞춘다. 공백으로 들여쓰지 않는다(PowerPoint에서 줄이 다시 밀림).
- 정보가 1개뿐인 칸, 한 정보가 칸 폭 때문에 두 줄로 나뉜 칸(예: 'B.O · 메가오더' / '사전예약'), 흐름도 상자 안 글자에는 붙이지 않는다.
- 글머리 줄은 문장 끝 온점을 찍지 않는다(개조식, 4-C-12).

### 4-B. 기능 보고형 (사내 중간 보고, 기능 소개, 개발 요청 공유)

기준 덱: 「신규 오픈 매장 프로모션 고도화 3개 기능 중간 보고」 개선본(2026-10-02, 6장).

#### 4-B-1. 제작 절차

1. **장 설계**: 기능을 실제 진행 시점 순서로 나열한다. 개발 요청 번호 순서가 아니다.
   - 기능마다 2장을 둔다: '기능 소개' 1장 + '화면 상세' 1장.
   - 단계 정의를 쓴다: `[n단계 · 시점, 내용]`.
   - 단계는 1~4개까지 쓸 수 있다. 흐름 헤더 폭은 단계 수에 맞춰 자동으로 나뉘고, 글자 수 한도는 4-B-6의 단계 수별 값을 따른다.
   - 5개 이상은 한 줄에 읽히는 폭이 나오지 않아 `createDeck`이 오류를 낸다. 시점이 같은 기능을 한 단계로 묶거나(단계 안에서 장을 늘림), 덱을 나눈다.
2. **패턴 선택**: 각 장에 4-B-4의 패턴 A~F 중 하나를 고른다.
   - 기능 소개 장은 A·C·E 중 하나다.
   - 화면 상세 장은 B·D·F 중 하나다.
3. **이미지 준비**: 4-B-5 규칙에 따라 화면안을 PNG로 잘라 둔다.
4. **스크립트 작성**: `example_interim_report.js`를 복사한 뒤 문구·이미지 경로만 바꾼다. 4-B-6의 한 줄 글자 수를 참고해 줄을 직접 나눈다.
5. **생성 · 검증**: `node 스크립트.js out.pptx`로 생성한 뒤 `validate.py`를 통과시킨다. 줄 탈락 오류로 멈추면 1-2의 순서대로 고친다.
6. **렌더 검수**: PDF로 바꾸고 이미지로 렌더해서 7장 체크리스트를 확인한다.
7. 기준 덱이 있으면 `compare_layout.py`로 좌표를 비교한다.

#### 4-B-2. 구성 규칙

- 배경은 전부 white로 한다. 샌드위치 구조는 적용하지 않는다.
- 상단 표시는 'n단계'로 쓴다(기준 덱은 1~3단계). '기능 n'은 쓰지 않는다. 개발 요청 번호는 발표자 노트에만 쓴다.
- 공수·M/D·기술 분석·개발사 확인사항은 넣지 않는다.
- 첫 장(기능 소개)에만 진행 현황을 쓴다. 형식: `진행 현황: M/D(요일) 개발 요청 발송 · 상태  |  운영 담당: 부서(역할)`.
- 모든 장 오른쪽 아래에 `YYYY-MM-DD 중간 보고 · n / N`을 넣는다. `save()`가 자동으로 넣는다.

#### 4-B-5. 화면 이미지 준비 (`scripts/crop_screens.py`)

- 개발 요청 메일·기획서에 첨부된 화면안을 잘라 쓴다. 새로 그리지 않는다. PNG로 저장한다(코드가 PNG 크기를 읽음).
- 휴대폰 화면은 상태바부터 화면 하단까지 자른다. 다른 화면의 화살표나 주석이 같이 잘리지 않게 2~5px 안쪽으로 자른다.
- 잡티는 주변 배경색으로 덮는다: 붙여넣기 아이콘, 화살표 조각, 페이지 주석, 보라색 배경 띠 등. 흰색으로 덮지 말고 실측한 배경색을 쓴다(예: 248,248,248).
- 표 화면이 작아 읽히지 않으면 머리부와 4~6행만 잘라 폭 12.33으로 키운다(패턴 F).
- 이미지 대체 텍스트는 `alt`에 화면 설명을 넣는다. 파일 경로가 들어가면 안 된다.

| 화면 구조(바텀시트) | 화면 2개 h 4.6(x 0.95, 간격 0.55) + 영역 번호 + `table({x:6.0, colW:[0.4,1.6,1.0,3.73], rowH:0.56, size:10.5})` 7행 + `key({x:6.0, y:6.3, w:6.73})` | 개요: 시트 · 팝업 구조 |
| **개요(중간 보고, v3.8)** | `table(['단계','적용 시점','개발 과제','대상 시스템'], {y:1.95, colW:[2.81,2.12,5.37,1.83], rowH:[0.62,0.86,0.62], headH:0.4, size:11})` + 단계 연결 박스 4칸(y 4.75, 폭 2.56, 높이 0.79, x 0.6부터 3.19 간격, 14pt, 'n단계:' 굵게) + `key({y:5.85, h:0.5, size:18})` | 중간 보고 개요 |

- 폭 검산: 화면 n개 폭 합 = n × h × 비율 + (n−1) × gap ≤ 12.13. 6화면을 h 4.2로 두면 넘친다(4.0으로).
- 높이 검산: 화면 y + h + 0.72(캡션·설명) ≤ 6.9. 표 바로 아래 캡처·강조는 0.2in 이상 띄운다.
- 화면 오른쪽 설명(`notes`)의 x는 마지막 화면 오른쪽 끝 + 0.4 이상. 화면을 빼서 1개만 남으면 오른쪽 표를 화면 쪽으로 당겨 빈 폭을 없앤다.
- **상태 전이 장**: 캡처는 반드시 시간 순서(왼쪽 → 오른쪽)로 놓고, 열마다 같은 위쪽 기준선에 맞춘다. 캡처 높이가 다르면 아래로 남는 공간을 비워 두고 표의 열과 1:1로 맞춘다. 상태 이름은 캡처 위 캡션과 표 머리행에 같은 문구로 쓴다. 상태 위치가 흩어져 "어떤 구분인지 모르겠다"는 피드백(2026-10-20)을 막기 위한 배치다.
- 화면 구조 장의 영역 표시: 캡처 위 영역마다 doc-accent-gold 1.25pt 테두리(안쪽 0.02in) + 왼쪽 바깥(x − 0.29) 지름 0.24 골드 원에 흰 번호 10pt Bold. 표 첫 열 번호와 1:1로 맞춘다. 영역은 빈틈 없이 위에서 아래 순서로 나누고, 표 '구분'은 재사용 · 확장 · 신규 개발 · 이미지 · B.O 등록 중 하나. 현행 모듈을 그대로 쓰는 영역(헤더 등)은 동작 설명을 붙이지 않고 '재사용'으로만 둔다.
- 화면 구조 표 오른쪽 끝(x + 폭)이 12.73을 넘지 않고, 3단 마지막 단 오른쪽 끝 + 0.1 ≤ 표 x 인지 검산한다(첫 시도에서 0.02in 겹친 사례).

#### 4-C-5. 제작 절차

1. 화면은 프로토타입에서 Playwright 2배 해상도로 다시 캡처한다(이전 덱 이미지 재사용 금지: 문구·쿠폰명이 바뀌어 있을 수 있음). 팝업은 요소 크롭(여백 12px) 후 높이를 맞춰 패딩한다.
   - **전체 길이 화면**(화면 구조 장): 스크롤 영역을 (높이 − 40px)씩 내리며 캡처해 스크롤 영역 부분만 이어 붙이고, 맨 위 헤더와 맨 아래 하단 고정 버튼은 첫 캡처에서 잘라 붙인다. 영역 좌표는 같은 때 DOM `getBoundingClientRect()`로 받아 JSON에 저장해 번호 위치에 쓴다. 단 나누는 지점은 섹션 경계(다음 섹션 top)로 잡아 앞 섹션 배경이 다음 단 맨 위에 남지 않게 한다. 아주 긴 영역(유의사항 등)은 잘라 쓰고 점선으로 생략을 표시한다.
   - **상태 화면은 사용자가 처음 보는 기본 화면으로 캡처한다.** 예: 종료 상태는 진입 직후 상단 종료 딤 화면(scrollTop 0)이 기본이고, 아래 랭킹은 사용자가 스크롤해서 본다. 캡처 설명도 "상단 종료 딤 · 랭킹은 스크롤"처럼 기본 화면 기준으로 쓴다.
2. 장 순서: 표지 → 목차(읽는 순서) → [간지 개요] 핵심 정책 · 고객 흐름 · **화면 구조(상세 · 바텀시트)** · 재사용/신규 · 용어 → [간지] 기능 영역들(고객이 겪는 순서) → [간지] 연동 · 랭킹 → [간지] 운영 · 개발 범위(B.O · 데이터 · 개발 영역 · 놓치기 쉬운 점) → [간지] 부록. 장마다 위 배치 중 하나를 고른다.
   - **중간 보고(흐름도 중심, v3.8)**: 표지 → 개요(단계 표 + 단계 연결 박스 줄 + 핵심 한 줄) → [간지] 1단계 → 흐름도 장 → [간지] 2단계 → 흐름도 장 … 단계마다 간지 1장. 간지 설명 줄은 "개발 요청 n번 · 적용 시점, 한 줄 요약", 목록에는 담은 장 번호 · 제목. 목차 장은 장이 12장 이하면 생략한다.
   - 장 번호는 손으로 적지 않는다: `sec(name, desc, look)`로 간지를 만들고 일반 장은 `sl({id, ...})`로 만들어 `count()`로 번호를 모은 뒤, 덱 끝에서 간지 목록 · 목차 표 · 체크리스트 관련 장 번호를 채운다(부록 D 끝 예시). 장을 넣고 빼도 번호가 저절로 맞는다.
   - 기획서에는 기본으로 넣지 않는다(사용자 지시 2026-10-19, 요청할 때만): 서버 저장 데이터 · API, 예외 처리 · 안내 문구, 태스크별 공수(내부 참고값은 벤더 공유 금지), 남은 결정 항목, 전체 일정 · 함께 보는 자료. 확인이 필요한 항목은 덱 대신 답변에서 따로 알린다.
3. **프로토타입이 키값이다.** 덱의 따옴표 안 화면 문구("...")는 프로토타입 문구 원본(MSG 등)과 자동 대조해 불일치를 0으로 맞춘다. 현행 화면 모듈에 없는 UI(예: 출석 경품 칸에 '기간 부족' 사유 문구)를 기획서나 프로토타입에 임의로 더하지 않는다. 프로토타입을 고치면 검증 → 재캡처 → 덱 재생성 → PRD 순서로 동기화한다.
4. `node 스크립트.js out.pptx` → `check_text.py`('글꼴·줄바꿈 통과') · `check_clean.py`('깨끗함') · `validate.py` 통과.
5. PDF → 이미지로 전 장 렌더해 겹침(표와 핵심 한 줄, 캡션과 표, 설명 제목 줄바꿈, 화면 구조 장의 단과 표)을 눈으로 확인한다. `check_text.py`는 폭 추정이라 렌더에서 넘치는 설명 제목은 짧게 고친다. 렌더 후 장 제목을 추출해 목차 · 간지 · 체크리스트 장 번호와 대조한다.
6. 사용자가 PPT를 직접 고쳐 보내면 그 파일을 기준본으로 삼는다: 텍스트 · 좌표 · 글자 크기를 추출해 생성 스크립트 결과와 비교하고(바뀐 도형만 출력), 사용자가 고친 문구 · 배치 · 크기를 스크립트에 그대로 옮긴 뒤 다음 수정을 얹는다.
7. 사용자에게 넘기기 전에 4-C-6 최종본 규격 점검을 모두 통과시킨다.

#### 4-C-6. 최종본 산출물 규격 (v3.7, 사용자 지시 2026-10-20)

처음 문서를 보는 사람(개발사 · 타부서)은 다듬은 과정을 모른다. 전 · 중 · 후가 섞이면 오히려 헷갈리므로 **최종 정책 · 기능 · 흐름만** 쓴다.

1. **버전 표기**
   - 확정 전에는 모든 산출물(기획서 · PRD · 프로토타입 · 검증 스크립트)의 파일명 · 표지 · 노트 · 기준 자료 표기를 **v0.2로 통일**한다. 수정해도 버전은 올리지 않고 파일명 날짜만 바꾼다. 확정되면 v1.0으로 승격한다.
   - 표지 문서 종류 줄은 '문서 종류 + 버전'만 쓴다(예: "앱 이벤트 기획서 v0.2"). "1차 확정" · "수정본" · "확정 시 v1.0" 같은 상태 문구는 넣지 않는다.
   - 표지 날짜 줄: `YYYY-MM-DD · 부서 · 핵심 기간`(예: "2026-10-20 · 마케팅1팀 서비스기획 · 투표 2026.11.23(월) ~ 12.06(일)").
2. **작업 이력 금지**(본문 · 표 · 핵심 한 줄 · 발표자 노트 모두): 피드백 날짜, "피드백 반영", "~를 제거 · 대체 · 변경 · 폐기", "(현행 동일)", 대안 서열 · 결정 경위, 공수 절감 사유를 쓰지 않는다. 이력은 업무 이관 문서(`work-handoff-prompt`)에만 남긴다.
3. **없어진 것은 언급하지 않는다.** "오픈 전 화면 없음", "문구 분기 없음" 대신 최종 규칙을 긍정형으로 쓴다("노출 시작 = 투표 시작", "회차와 관계없이 같은 문구"). 미정 항목은 [확인필요(부서)]로만 쓴다([미결] · "검토 중" 혼용 금지).
4. **같은 규칙은 모든 위치에 같이 쓴다.** 한 규칙을 고치면 그 규칙을 설명하는 모든 장(구조 · 기능 · 로직 · 체크리스트 · 용어)과 PRD를 함께 고친다.
   - 대칭 규칙은 양방향을 모두 적는다. 예: "한쪽을 고르면 0.3초 뒤 다른 탭으로 이동 / 음료 → 푸드, 푸드 → 음료 모두 같음".
   - 고친 뒤 핵심어로 전체 텍스트(노트 포함)를 검색해 옛 표현이 남지 않았는지 확인한다.
5. **모순 대조**: 장끼리 조건이 충돌하지 않는지 비교한다. 예: 앱 푸시 장 "마지막 날 달성분 08시 발송 취소" vs Braze 장 "마지막 날 미발송" → 한 표현("마지막 날 달성분은 발송 대상 아님")으로 통일.
6. **발표자 노트**: 첫 줄에 근거를 쓴다(예: "근거: 프로토타입 v0.2 · PRD v0.2."). 이어서 그 장의 최종 규칙 · 예시값 여부 · 확인 필요 부서만 쓴다.
7. **산출물 세트**(사용자가 "산출물 세트"를 요청하면): 기획서 pptx + PRD docx(`work-writing-patterns`의 PRD 구성) + 프로토타입 html + 검증 스크립트 py + 이관 md. 파일명 `[번호]) 메가MGC커피_[프로젝트]_[산출물]_v0.2_YYMMDD`(번호는 사용자 폴더의 기존 체계를 따름). PC 저장은 `dated-folder-save`로 오늘 날짜 폴더에 둔다. 같은 날 다시 저장하면 새 파일명으로 저장하고, 예전 파일 삭제는 사용자에게 알리기만 한다.
8. 점검: 전체 텍스트에서 "반영 · 제거 · 대체 · 변경 · 폐기 · 1차 · 확정 시 · v1." 등 이력 표현과 옛 버전 문자열을 검색해 0건인지 확인한다(정책 문구로 쓰인 "변경 불가" 같은 단어는 예외).
9. **결정 과정 미노출(v4.0, 사용자 지시 2026-10-21)**: 확정된 정책은 최종 기준만 쓴다. 선택지 · 추천안 · 1~3순위 · 「○○ 권고와 같음」 · 「결정 ○번」 · 「(확인 중)」 · 「공수가 적정하면 도입」 같은 판단 문구를 남기지 않는다. 결정 장은 「정책 기준 N가지」(항목 | 기준 | 비고)로 쓰고, 항목이 빠지면 N과 이를 가리키는 모든 문장 · 간지 목록을 같이 고친다.
   - 쓰지 않기로 한 기능 · API는 흔적 없이 지운다(번호 · 표 행 · 흐름도 단계 · 용어 · 부록 불일치 행까지). 꼭 설명이 필요하면 번호 원본 장 각주 1줄로만 쓴다(예: "로그인 유지는 자체 토큰으로 하므로 토큰 인증 API는 쓰지 않습니다").
   - 문서 전반의 결론이 바뀌면 개요 수치(예: API 11종 → 9종), 목차 설명, 간지 설명, 핵심 한 줄까지 같은 값으로 맞춘다.

#### 4-C-7. 흐름도 논리 검수 (v3.8, 사용자 지시 2026-10-20)

흐름도 장은 만든 뒤 장마다 한 번씩 아래를 확인하고 고친다. 고친 내용은 답변에서 표(장 · 문제 · 고친 내용)로 알린다.

1. **처리 순서 = 요구사항 순서**: 요구사항에 처리 흐름(예: 매장 확인 → 등록 → 쿠폰 판단 → 화면 → 안내)이 있으면 상자 순서를 그대로 따른다. 화면 노출 상자를 판단보다 앞에 두지 않는다.
2. **성립하지 않는 분기 제거**: '아니요'로 가면 그 화면 자체가 없는 판단(예: 매장 미노출인데 '일반 표시')은 빼고, 시작 상자 조건으로 옮긴다.
3. **판단 문구가 모든 경우를 맞게 가르는지**: 이미 처리된 대상이 잘못 걸리는지 본다(예: 이미 등록된 매장이 '한도 초과'로 빠짐 → '새 등록 한도 초과?'). 예외는 상자 글에 "(이미 등록 매장은 생략)"처럼 적는다.
4. **막다른 길 없음**: 모든 판단은 나가는 길 2개 이상에 분기 이름이 있고, 시작·끝 · 안내 상자가 아닌 상자는 다음 상자로 이어진다. 검증 실패 · 오류 안내는 "수정 후 다시 …" 되돌림 화살표로 입력 단계에 연결한다.
5. **모이는 지점 명시**: 여러 결과가 같은 화면 · 안내로 모이면 화살표로 합치거나 핵심 한 줄로 밝히고, 결과별 안내는 표(결과 × 조건)로 정리한다. 버튼을 누른 뒤 처리(예: [알림 받기])도 표 행으로 넣는다.
6. **진입 경로 일반화**: 사용자 진입이 여러 경로면 시작 상자에 모두 쓴다(예: "쿠폰 화면 진입(푸시 · 직접)"). 앞 단계의 선택 행동(푸시 발송)이 유일한 경로처럼 보이지 않게 한다.
7. **시간이 떨어진 처리**: 나중에 일어나는 처리(예: N일 후 발급)는 같은 줄 오른쪽 별도 상자로 두고 조건(진입 시 · 대상 제외)을 상자 글이나 노트에 쓴다.
8. **분기 이름 배치**: 주 흐름(오른쪽)은 '예', 예외(아래)는 '아니요'가 되게 판단 문구를 정한다(예: '이미 받음?' → '처음 받음?'). 왼쪽으로 가는 짧은 분기는 한 글자 이름('예')만 쓴다. 분기 이름이 옆 상자와 겹치면 문구를 바꾸거나 상자를 옮긴다.
9. **번호 대응**: 상자 속 요구사항 번호(①~⑬, 요건 1~12)가 근거 문서와 맞는지, 장 노트 첫 줄 근거와 같은지 본다.

#### 4-C-8. 흐름도 부품과 배치 (v3.8, 부록 E)

| 모양 | 의미 | 서식 |
|---|---|---|
| 둥근 상자(다크 3B2A20, 흰 굵은 글) | 시작 · 끝 · 다음 장으로 이어짐 | 장마다 시작 1개 + 끝 1~2개 |
| 상자(soft F3EEE8) | 앱 · 서버 · B.O 처리 | 요구사항 번호를 글 끝에 |
| 마름모(흰 바탕, 다크 1pt 테두리, 굵은 글) | 판단 | 글 2줄 이내, 줄당 8자 안팎, 끝에 '?' |
| 상자(흰 바탕, muted3 A6968A 1pt 테두리) | 손님 · 운영자에게 보이는 안내 · 오류 | 화면 문구는 프로토타입 원본 그대로 작은따옴표 |

- 범례: 모양 4종 + 이름을 영역 이름 줄(y 0.42) 오른쪽에, 오른쪽 끝 12.73 기준으로 둔다.
- 5열 격자: 상자 폭 2.1, 열 중심 x = 0.6 + 1.05 + i × (12.13 − 2.1) / 4 (i = 0~4), 판단 높이 0.85, 처리 높이 0.66. 열 사이 0.41에 화살표 + 분기 이름이 들어간다.
- 행 간격 1.0~1.15in. 한 장 최대 5행(y 2.35 · 3.35 · 4.3 · 5.25 · 6.3). 본문 하단 6.85 이내.
- 배치 3종(겹침 없이 통과):
  - **ㄹ자 흐름**: 1행 왼→오, 끝 열에서 아래로 꺾어 3행 오→왼, 다시 아래 5행 왼→오. 예외 상자는 판단 바로 아래 행.
  - **두 구역**: 위 구역(B.O · 운영) / 아래 구역(앱 화면 판단)에 11pt 굵은 구역 이름. 여러 '아니요'가 모이는 결과는 해당 열 폭을 덮는 넓은 상자 1개.
  - **세로 흐름 + 오른쪽 표**: 왼쪽 x 0.6~3.4 세로 흐름(간격 0.1, 판단 뒤 0.25), 오류 상자는 판단 오른쪽(중심 x 5.15), 되돌림 선은 x 6.75로 올라가 입력 단계 오른쪽에 붙임. 오른쪽 x 7.25~12.73에 규칙 표 + 핵심 한 줄.
- 흐름도 아래 결과 × 조건 표를 둘 때: 핵심 한 줄(h 0.42, 15pt) 아래 0.1, 표 행 0.4 · 11pt.

#### 4-C-9. 개발 연동 통합본 · API 연동 정의서 (v4.0, 기준 덱 「앱카드 연동 통합본 v0.12」 표지 포함 81장)

개발사 · 연동사 · 결제대행사가 함께 보는 연동 문서다. 기획서(4-C-5 기본 제외 항목)와 달리 API · 처리 흐름 · 예외 · 공수 범위 장을 넣는다.

1. **장 구성**: 표지 → 읽는 순서 → [간지] 개요 → 확정 정책 → 화면 명세 → 연동 구조 · API → 처리 흐름 → 예외 처리 → 결제대행사 · 정산 → 개발 범위 · 운영 → 미결 · 확인 필요 → 부록(문서 간 불일치 · 용어). 간지 목록은 2열 12개까지(`kit.js` `finish`).
2. **개요 필수 장**
   - 결론 · 핵심 수치(`stats`) + 정책 라벨 표 + 요약 연동 구조 도식
   - 독자별 먼저 볼 장: 「먼저 볼 장」 칸에 영역 이름과 장 범위를 같이 쓴다(예: "정책(10~19) · 화면(20~26)"). 범위 숫자는 덱 끝에서 다시 계산한다.
   - 앱 구조(아키텍처) 도식: 새 연동의 데이터 흐름에 순서 번호 원(지름 0.26in, 진갈색, 흰 숫자 10pt)을 붙이고, 아래 1줄 "※ 1~n은 ○○ 데이터 흐름 순서이며, 번호 없는 선은 현행 흐름입니다". API 번호(①)와 겹치지 않게 흐름 번호는 원 안 숫자로 쓴다.
   - 구성 요소 표: 구성 요소 | 쓰는 흐름(로그인 · 결제 · 카드 관리) | 위치 | 하는 일 | 개발 주체 · 구분.
3. **개발 주체 · 구분 값**: "CJ ONS · 기존 수정", "CJ ONS · 신규 개발", "핏콜라보 · 제공", "카드사", "CJ ONS(OnePG) · 범위 확인"처럼 주체와 구분을 함께 쓴다. "CJ ONS(신규)"처럼 괄호로 줄인 표기는 쓰지 않는다.
4. **정책 표의 개발 구분 열**(상태 열 대신): 현행 구조와 맞지 않으면 "[[신규 개발]](현행 1:1 구조와 다름)", 현행 화면 · 기능에 요소만 더하면 "기존 수정(○○ 추가)", 정해지지 않았으면 [확인필요(부서)]. "적용" · "적용(구조 개선)" 같은 뜻이 흐린 값은 쓰지 않는다.
5. **번호 체계 원본 장**: API · 단계에 번호(로그인 ① · 결제 ②)를 쓰면 번호 목록 장 1장을 원본으로 둔다(번호 | API | 호출 경로 | 서버 · 규격 | 역할). 그 장 핵심 문장에 "번호는 이 장이 원본"이라고 쓴다.
   - 번호를 쓰는 다른 모든 장 하단(x 0.6, y 7.02, w 10.9, 9pt muted, 이름 "출처")에 "※ API 번호(로그인 ① · ② / 결제 ①~⑥ / 카드 관리 ①)는 N장 목록 기준입니다"를 둔다(`add_source_line`).
   - 본문에서는 번호만 쓰지 않고 이름과 함께 쓴다: "결제 ②"(×) → "결제 거래번호 발급 ②(requestTid.mv)"(○). 표의 번호 열 · 좁은 칸은 예외.
6. **키(한글 이름) 표기**: 파라미터 · 응답 키는 처음부터 끝까지 "키(한글 이름)" 형식으로 쓴다(예: transNo(인증 거래번호), deviceType(기기 구분), payType(카드 구분)). 호출값 · 키값 · 식별값 표와 정책 표 모두 같다. 한글 이름은 4-C-11 사전을 따른다.
   - 호출값 표: 호출값 | 필수 | 설명 | 적용값. 적용값 칸은 값과 이유를 함께 쓴다(예: "N(Webview의 공통 웹 컴포넌트에서 호출)", "보내지 않습니다(고객이 인증 모듈에서 카드사 선택)").
   - 키값 표: API(번호 / 이름 / 호출명 3줄) | 역할 | 보내는 값 | 받는 값. 보내는 값 · 받는 값은 의미 묶음마다 "- " 줄. 한 장에 안 들어가면 글자를 줄이지 말고 장을 나눈다("결제 API 키값 ① · ②").
7. **상태 · 구분 값의 기준 시점**: "기존 카드 · 새 카드"처럼 상태로 나뉘는 값은 앱 처리 흐름에서 언제 생기고 어느 화면 요소에 보이는지 각주로 정의한다(예: "기존 카드는 앱카드 로그인 인증 · 이전 결제 · 카드관리 페이지 등록으로 이미 등록된 카드이며, 주문하기 진입 때 계정 목록 조회 ①로 받아 화면 2 · 3의 1a에 보입니다").
8. **처리 구조 장**: 이동 · 복귀처럼 여러 단계가 이어지는 주제는 왼쪽 설명(w 6.0) + 오른쪽 세로 구조 도식(x 7.0, w 5.73, 상자 높이 0.6, 상자 사이 0.23 화살표, 플랫폼 갈래는 2칸 폭 2.75)으로 그린다. 색은 업체 색 규칙(핏콜라보 연빨강 · 빨강 테두리, Webview 연베이지, Native 진갈색, 외부 흰 바탕)을 따른다.
9. **채택한 방식만 쓴다**: 쓰지 않는 방식과의 비교표(예: 앱 직접 호출 vs 공통 웹 컴포넌트)는 만들지 않는다. 채택한 방식을 항목별(요청 → 표시 → 결과 수신 → 서버 확정 → 복귀 → Native 작업)로 자세히 쓴다.
10. **현행 비교 열은 꼭 필요할 때만**: 범위 설명 장(예: 카드 관리)은 새 기능의 범위 · 기능 · 메가MGC커피 개발 몫만 쓴다. 현행 비교는 "현행과의 차이" 장 하나에 모은다.
11. **흐름도 · 송수신 이미지**: 이미지 위에 덧그리지 않는다. 원본 정의서 장을 먼저 고친 뒤 150dpi로 렌더해 같은 비율로 자르고, 덱 · docx 그림은 위치 · 크기를 두고 이미지만 바꾼다(`replace_picture`). 자르기 비율(흐름도 세로 0.235~0.865, 송수신 0.235~0.93)은 이관 문서에 남긴다. 단계를 빼면 번호를 다시 매기고, 장 제목의 단계 수("16단계")와 단계표를 같이 고친다.
12. **내부 판단 장 구분**: 정책 기준 · 법무 확인 장은 내부 자료다. 개발사 · 연동사에 보낼 때는 빼거나 정제본을 따로 만든다.

#### 4-C-10. 사용자 판 직접 편집 (python-pptx, v4.0, 부록 F)

1. 사용자가 다듬은 pptx를 받으면 그 파일이 기준이다. 다시 생성하지 않고 `scripts/pptx_edit.py`로 고친다. 사용자의 배치 · 색 · 글자 크기는 바꾸지 않는다.
2. **칸 문구 교체**: `set_cell`은 칸 폭 − 0.24in에서 의미 단위로 줄을 나누고, 빨강이 아닌 첫 런 서식을 원본으로 쓴다(빨강 런을 원본으로 잡아 문장 전체가 빨갛게 되는 사고 방지). 줄 수가 바뀌면 `fit_rows`로 행 높이를 다시 계산하고, 표 아래 요소(핵심 한 줄 · 각주 · 도식)와 겹치는지 `bottom()`으로 확인한다.
   - 겹치면: 문장 축약 → 열 폭 재분배(합 12.13) → 아래 도식을 내림(핵심 한 줄 top ≤ 6.44) → 장 나누기 순서로 고친다. 글자 크기를 줄이는 것은 마지막이며 10.5pt 아래로 내리지 않는다.
   - 칸 폭을 바꿨으면 그 표 전체를 `rewrap_table`로 다시 나눈다(옛 폭 기준 줄바꿈이 남아 단어가 중간에서 끊기는 사고 방지).
3. **열 · 행 바꾸기**: 열을 빼거나 더할 때는 `tblGrid`의 `gridCol`과 모든 행의 `tc`를 같이 바꾼다(`add_col` · `del_col`). 열만 줄이고 `gridCol`을 남기면 표가 화면 밖으로 나간다(`check_clean` "화면 밖").
4. **장 추가 · 분할**: `duplicate_slide`로 원본 장을 복제해 바로 뒤에 넣고 `renumber(p, 새 장 번호)`로 쪽 번호(n / N), 간지 목록 번호, 본문 "N장" · "N~M장" · "(N~M)" 참조를 다시 맞춘다. 목차 표 범위는 간지 위치로 다시 계산하고, 새 장의 간지 목록 항목은 2열 배치로 다시 놓는다.
5. **용어 일괄 치환**: 런 단위로 바꾸고, 한 문구가 여러 런에 걸친 곳은 목록으로 받아 따로 고친다. 치환 뒤 넘친 칸은 `check_text.py` 목록대로 `merged_text` → `set_cell`로 다시 나눈다.
6. **피드백 장 번호 확인**: "p.N"은 장 제목 · 내용과 대조한다(4-C-2). 2026-10-21에도 "71p"가 72장(결정 장)이었다.
7. 검수: `check_text.py` · `check_clean.py` · `validate.py` → 전 장 렌더 확인(표와 아래 도식 겹침, 렌더에서 두 줄로 넘친 제목). 원본에 있던 `revisionInfo` 검증 경고는 그대로 둔다.

#### 4-C-12. 문체 · 기호 · 줄바꿈 · 강조 · 보고 구조 (v4.1, v4.2 개정 2026-10-26, 기준 덱 「앱카드 연동 통합본 v0.25」 표지 포함 88장 · 사용자 수정 4장)

사용자가 4장을 직접 고친 판을 기준 서식으로 삼았다. 사용자가 한 장을 고쳐 보내며 "전 화면 확장"을 요청하면, 그 장에서 바뀐 서식 · 서술 패턴을 모두 뽑아(원본과 run 단위 비교) 같은 성격의 모든 위치에 적용한다.

1. **문체 분리**
   - 제목(최상단): 개조식 「토픽: 핵심 서술」. 토픽은 그 장이 다루는 대상(예: 「결제 전 체크」), 서술은 결론을 명사 · 개조식으로 끝낸다(예: 「결제 전 체크: 화면별 체크 통과 뒤에만 결제 거래번호 요청」). 한 줄(24pt, 폭 보정 0.93) 안에 들어가야 한다. 제목 전체를 본문색(2E241D)으로 쓰고 부분 색은 넣지 않는다.
   - 서술형: 핵심 문장, 핵심 한 줄(장의 결론을 읽는 사람에게 말하는 문장).
   - 개조식: 표 칸, 설명 · 본문 상자, ※ 각주, 도식 상자 문단. 끝맺음은 「~함 · ~음 · ~됨」, 「X입니다」 → 「X」, 「엽니다」 → 「열어 줌」, 「만듭니다」 → 「만듦」(어색한 「엶」 금지). 끝 온점 없음.
   - 개조식으로 바꿔도 뜻이 같아야 한다. 주어 · 목적어를 지우지 않는다(「승인 취소」 (×) → 「메가MGC커피 서버가 승인 취소 ⑤ 호출」 (○)).
2. **문장 명확성**: 모든 문장 · 항목에 누가(주어) 무엇을(목적어)을 쓴다. 「적용」 같은 상태 단어만 남기지 않고 뜻을 쓴다(「적용」 → 「정책 확정」, 「오감」 → 「송·수신」). 조각 문장은 술어까지 완성한다. 같은 사실을 장끼리 다르게 쓰지 않는다.
   - 표의 행 이름은 상태가 아니라 토픽으로 쓴다(「확인 필요 1」 → 「사전 작업」, 「확인 필요 2」 → 「데이터 저장」).
   - 한 문장에 주어가 다른 두 내용이 나란히 있으면 주어 앞에 ①②를 붙인다(「①인증 거래번호(transNo)는 로그인 인증, ②결제 거래번호(tid)는 결제 승인」). 3단계 이상 이어지는 순서(「A → B → C」)도 단계마다 ①②③을 붙인다. 단, API 번호(①~⑥)를 쓰는 칸 · 보내는 쪽 → 받는 쪽 경로에는 붙이지 않는다(번호 뜻이 겹침).
3. **기호 용례**(의미 하나에 기호 하나):

| 기호 | 쓰는 곳 | 쓰지 않는 곳 |
|---|---|---|
| `- ` | 표 칸 · 설명의 정보 단위 글머리. 표 설명 열은 항목이 1개여도 「- 」로 시작 | 빈 칸 |
| `·`(앞뒤 공백) | 한 줄 안 나열(「주문번호 · tid」). 합성어는 붙여 씀(「송·수신」) | 글머리, 줄 머리 |
| `~` | 범위(「11~23」, 「2026.04~2028.03」) | 나열 |
| `—` | 빈 표 칸 1글자, **가운데 정렬** | 제목 · 영역 이름 · 간지 목록 · 문장 안 구분 |
| `: ` | 제목의 토픽 구분, docx 제목 · 그림 설명의 부연, 「값: 뜻」 | |
| `( )` | 영역 이름 · 간지 목록의 부연(「결제 정책(판단 · 경로)」) | |
| `•` · `–` | 쓰지 않음 | |

   - 「- 」를 붙이는 표 열: 설명 · 기준 · 처리 · 규칙 · 비고처럼 문장형 정보가 들어가는 열. 이름 열(첫 열), 머리행, 값 · 코드 · 번호 · ● · 상태 · 개발 구분 · 위치 · 호출값 · 고객 화면 문구(그대로 보여 줄 문구) 열에는 붙이지 않는다. 한 열에 글머리 칸이 하나라도 있으면 그 열 전체에 붙인다(`format_pass.include`).
   - 이어지는 줄은 「- 」 폭만큼 문단 들여쓰기(marL). 칸 첫 글자가 빨강이어도 「- 」는 본문색으로 둔다.
4. **줄바꿈**(`edit_lib.wrap`):
   - 폭 보정 0.82(0.88에서 PowerPoint가 「변경하 / 기」처럼 단어를 자름). 「- 」를 앞에 붙이기만 하는 칸은 다시 나누지 않고, 폭을 넘는 칸만 다시 나눈다.
   - 한 덩어리로 묶어 나누지 않는 것: 「A · B」 나열, 여는 괄호부터 24자 이하 괄호, 확인 태그, 고유 명칭(`GLUE`: CJ ONS, 메가MGC커피 서버, 핏콜라보 서버, 확인 필요, 처리 흐름, 연동 구조, 정책 기준, 카드관리 페이지, 공통 웹 컴포넌트, 인증 모듈, 결제 화면 등).
   - 나열만으로 된 정보는 줄 경계의 「·」를 뺀다. 다시 붙일 때는 괄호가 열려 있지 않은 줄에서만 「·」를 복원한다(「[핏콜라보 · CJ⏎ONS]」를 「CJ · ONS」로 만든 사고). 줄 머리 「·」 금지.
   - 빨강 [[ ]] 구간이 줄을 넘으면 줄마다 닫고 다시 연다. 괄호까지 빨강인 태그는 「[[[태그]]]」로 쓰고 끝 「]]」 뒤 「]」까지 한 구간으로 읽는다.
5. **표 맞춤**: 글이 바뀐 표만 맞춘다(글이 그대로인 표는 손대지 않음, 원래 하단 위치를 한도로 인정). 행 높이를 다시 계산하고, 아래 요소와 겹치면 핵심 한 줄을 6.44까지 내린 뒤 글자 크기를 0.5pt씩 줄인다(최소 10.5pt).
6. **강조**: 빨강은 기본 빨강 **#FF0000** 하나만 쓴다(글자 · 도형 선 모두, 이전 F53148 · D32F2F · docx C00000 대체).
   - 굵은 빨강은 현 시점 최종 정책 문구에만(정책 문구 장당 3곳 이하, 확인 태그는 따로 셈). 상태 값 · 개발 구분 값 · 표 머리 · 전체 문장은 강조하지 않음(예외: 개발 구분 열의 「신규 개발」).
   - 노랑 배경(badge-bg FDF9C9)은 「신규 개발」 칸에만.
   - 요약 띠(「라벨   내용」 한 줄 상자)는 라벨만 굵게, 내용은 보통 굵기.
7. **확인 태그(덱 · 정의서)**: 「[확인필요(부서): 내용]」 대신 누가 무엇을 해야 하는지 서술형으로 쓰고 빨간 굵은 글씨로 둔다.
   - 형식: 「[주체 (↔ 상대) 내용 확인 필요]」, 법무는 「[법무팀 (내용) 검토 필요]」. 예: 「[핏콜라보 ↔ CJ PG 연동 일정 검토 필요]」, 「[CJ ONS 현행 차감 시점 확인 필요]」.
   - 문장이 이미 판단 주체를 말하면 태그를 지운다(「적용 여부는 법무팀이 판단합니다」 뒤 태그 삭제).
   - docx는 문서 규칙대로 「[확인필요(부서)]」를 유지한다.
8. **보고 구조**:
   - 정해진 기준(「정책 기준 N가지」)은 개요 영역에, 마지막 「확인 필요」 영역에는 열린 항목만.
   - 독자별 안내 장은 독자를 맡은 범위로 나누고, 먼저 볼 장은 장 하나에 「- 」 한 줄.
   - 장을 옮기면 `move_remap.py`로 번호를 다시 매기고 docx · 이관 문서 · 검토 엑셀까지 같이 바꾼다.
9. **docx 동기화**: 글머리 「- 」 + 내어쓰기(글자 크기 × 0.68), 강조 빨강 FF0000, 표 칸 「~다.」 → 개조식, 제목 · 그림 설명의 「 — 」 → 「: 」. 처리한 칸은 요소(`_tc`) 집합으로 기억한다.
10. 점검: `check_text.py`의 [기호] 0건(「•」 · 「 — 」 · 줄 머리 「·」), [참고] 줄 끝 「·」는 문장 속 긴 나열인지 눈으로 확인, 렌더에서 제목 한 줄 · 단어 중간 줄바꿈 0건 · 빈 칸 「—」 가운데 정렬.

## 5. 문구 규칙

- **예시값**: 화면안의 금액·인원·날짜는 "(예시)"로 표기한다. 정책값은 B.O 설정 기준으로 쓴다.
  - 예: "B.O에서 정한 금액 할인 (화면은 1,000원 예시)"
- **기준점 명시**: 기간·한도에는 기준점을 함께 쓴다.
  - "최대 60일 연장"(×) → "최대 매장 생성일 + 60일"(○). 기준 덱 1장은 이 기준으로 고친다.
- **시점**: 오픈 전·당일·이후 같은 시점은 확정 정책과 대조한 뒤 쓴다.
- **용어**
  - 서비스 명칭은 작은따옴표로 쓴다: 'MY매장', '신규오픈'. 화면 캡처 속 UI 문구는 예외다.
  - 오프라인 매체는 "오프라인 홍보물"로 쓴다.
  - 사람 지칭은 한 덱 안에서 하나로 통일한다: 손님 또는 회원. B.O 메뉴명('MY매장 등록 회원')은 그대로 둔다.
- **제목**: 행동과 결과를 담은 한 문장으로 쓴다. 예: "매장 QR 한 번이면 'MY매장' 등록 + 쿠폰까지".
- **목적 문구**: "~합니다"로 끝나는 한 문장으로 쓴다. 두 문장이 필요하면 쉼표로 이어 한 문장으로 만든다(1-2).
- **문장 끝 줄바꿈**: 여러 줄 칸에서 문장이 온점으로 끝나면 다음 문장은 다음 줄에서 시작한다(1-2).
- **최종본 문구**: 작업 이력 · 없어진 기능 언급 없이 최종 규칙을 긍정형으로 쓴다(4-C-6).
- **단계 번호 = 개발 요청 번호(v3.8)**: 보고 덱의 단계 번호와 개발 요청 번호를 같게 쓴다. 이미 다른 번호로 요청이 나갔으면 다음 통합 메일에서 번호를 다시 매기고, 옛 번호 대응표는 메일에만 1회 넣는다(덱 · 정책 문서에는 새 번호만).
- **여러 정보는 하이픈 줄**: 1-4를 따른다.
- 개발 용어(API·인코딩·리다이렉터 등)는 쓰지 않는다. 과장 표현(혁신적인·스마트한·원활한·손쉽게·Seamless 등)도 금지한다.

8. 최종본(4-C-6): 버전 문자열이 파일명 · 표지 · 노트 · PRD에서 모두 같은가, 이력 표현 검색 0건인가, 대칭 규칙이 양방향으로 모든 위치에 적혀 있는가, 장끼리 모순이 없는가, 상태 캡처가 기본 화면인가.
9. 기준 덱 대비 좌표를 비교한다: `python3 compare_layout.py 기준.pptx out.pptx`. 패턴과 행 수가 같으면 불일치 0이 정상이다. 단계 수가 기준 덱(3단계)과 다르면 흐름 헤더 도형은 불일치로 나오는 것이 정상이다.
10. 연동 문서(4-C-9 · 4-C-11): 번호 원본 장이 있고 번호를 쓰는 장마다 출처 줄이 있는가, 본문에 번호만 쓴 곳이 없는가, 키가 모두 "키(한글 이름)"인가, 쓰지 않는 기능 · API 이름이 0건인가(번호 · 흐름도 이미지 포함), 개발 구분 값이 "신규 개발 / 기존 수정 / [확인필요]" 중 하나인가, 줄인 말(번호 · 모듈 · 주체 없는 서버 · PG) 검색 결과가 머리행 외 0건인가, 장을 넣고 뺀 뒤 쪽 번호 · 목차 · 간지 · 본문 장 참조가 맞는가.
11. 문체 · 기호(4-C-12): 제목이 「토픽: 서술」 개조식 한 줄인가, 표 칸 · 설명 · 각주가 개조식이고 핵심 문장은 서술형인가, 글머리가 「- 」(설명 열은 1개여도)이고 「•」 · 「 — 」 구분이 없는가, 빈 칸 「—」이 가운데인가, 빨강이 모두 FF0000인가, 렌더에서 고유 명칭 · 단어가 줄 경계에서 잘리지 않았는가, 빨강이 최종 정책 문구에만 장당 3곳 이하인가, 마지막 「확인 필요」 영역에 정해진 항목이 남아 있지 않은가.

## 부록 D. `scripts/slim.js` (4-C 부품, v3.6)

`scripts/`에 이 파일이 없거나 `divider`·`count`가 없는 이전 판이면 아래 코드를 작업 폴더에 `slim.js`로 저장해 쓴다. `fit_text.js`와 같은 폴더에 둔다. 좌표 · 색 · 글자 크기는 고치지 않고 함수 인자로만 내용을 넣는다.

```js
// slim.js — 기획서용 간결 레이아웃 (사용자 지시: 상단 흐름 헤더·장 구분 칩·순번 원 제거)
// 색·글꼴·줄맞춤은 mgc-ppt-template(v3.4)의 토큰과 fit_text.js를 그대로 사용한다.
const fs = require('fs');
const pptxgen = require('pptxgenjs');
const { fit } = require('./fit_text');
const F = 'Malgun Gothic';
const C = { yellow: 'FFDE00', text: '2E241D', dark: '3B2A20', muted: '7A6A5D', muted3: 'A6968A',
  soft: 'F3EEE8', tan: 'E2D9CF', beige: 'E6DDD4', white: 'FFFFFF',
  red: 'FF0000',      // 강조 빨강(v4.2, 기본 빨강): 본문 속 핵심 정책 강조(빨간 굵은 글씨) 전용
  newCell: 'FDF9C9'   // MGC badge-bg 토큰: 표의 '신규 개발' 등 구분 칸 배경 전용
};
// [[...]] 로 감싼 부분 = 빨간 굵은 글씨. fit()은 표시를 뺀 글자로 줄맞춤하고, 결과 줄바꿈 위치에 맞춰 강조 구간을 다시 입힌다
const strip = t => String(t).replace(/\[\[|\]\]/g, '');
function rich(marked, fitted, extra) {
  marked = String(marked);
  if (marked.indexOf('[[') < 0) return fitted;
  let plain = '', flags = [], on = false;
  for (let i = 0; i < marked.length; i++) {
    if (marked.startsWith('[[', i)) { on = true; i++; continue; }
    if (marked.startsWith(']]', i)) { on = false; i++; continue; }
    plain += marked[i]; flags.push(on);
  }
  const lines = [[]]; let p = 0;
  const push = (ch, red) => { const L = lines[lines.length - 1], last = L[L.length - 1]; if (last && last.red === red) last.t += ch; else L.push({ t: ch, red }); };
  for (const ch of fitted) {
    if (ch === '\n') { if (plain[p] === ' ' || plain[p] === '\n') p++; lines.push([]); continue; }
    const red = !!flags[p]; if (plain[p] === ch) p++; push(ch, red);
  }
  const runs = [];
  lines.forEach((L, li) => {
    if (!L.length) L.push({ t: ' ', red: false });
    L.forEach((g, gi) => {
      const o = Object.assign({}, extra || {}, g.red ? { bold: true, color: C.red } : {});
      if (gi === L.length - 1 && li < lines.length - 1) o.breakLine = true;
      runs.push({ text: g.t, options: o });
    });
  });
  return runs;
}
const NEW_CELL = ['신규 개발', '신규', '옵션 추가', '확장'];
const X0 = 0.6, W0 = 12.13;
const ratio = p => { const b = fs.readFileSync(p); return b.readUInt32BE(16) / b.readUInt32BE(20); };

function deck(title) {
  const pres = new pptxgen();
  pres.layout = 'LAYOUT_WIDE'; pres.title = title;
  pres.theme = { headFontFace: F, bodyFontFace: F };
  const pages = [];
  let hasCover = false;
  const T = (s, t, o, name) => {
    const r = fit(strip(t), { w: o.w, h: o.h, size: o.fontSize, bold: !!o.bold, name: name || '' });
    const opt = Object.assign({ fontFace: F, color: C.text, margin: 0, isTextBox: true, lang: 'ko-KR', valign: 'middle' }, name ? { objectName: name } : {}, o);
    if (r.charSpacing) opt.charSpacing = r.charSpacing;
    return s.addText(rich(t, r.text, r.charSpacing ? { charSpacing: r.charSpacing } : null), opt);
  };
  function cover({ kind, title, sub, meta }) {
    const s = pres.addSlide(); s.background = { color: C.dark }; hasCover = true;
    T(s, kind, { x: 0.9, y: 2.3, w: 11.5, h: 0.4, fontSize: 14, bold: true, color: C.yellow });
    T(s, title, { x: 0.9, y: 2.8, w: 11.5, h: 1.0, fontSize: 36, bold: true, color: C.white, valign: 'top' });
    T(s, sub, { x: 0.9, y: 3.9, w: 11.5, h: 0.5, fontSize: 16, color: C.tan, valign: 'top' });
    T(s, meta, { x: 0.9, y: 6.4, w: 11.5, h: 0.35, fontSize: 12, color: C.muted3 });
  }
  // 골격: 영역 이름(작은 글씨) + 제목 + 핵심 문장. 장식 도형 없음.
  function slide({ sec, title, msg, notes }) {
    const s = pres.addSlide(); s.background = { color: C.white };
    T(s, sec, { x: X0, y: 0.38, w: 6, h: 0.3, fontSize: 11, bold: true, color: C.muted }, '영역 이름');
    T(s, title, { x: X0, y: 0.7, w: W0, h: 0.6, fontSize: 24, bold: true }, '제목');
    if (msg) T(s, msg, { x: X0, y: 1.32, w: W0, h: 0.34, fontSize: 13, color: C.muted }, '핵심 문장');
    if (notes) s.addNotes(notes);
    pages.push(s); return s;
  }
  function phones(s, items, { x = X0, y = 1.95, h = 4.2, gap = 0.4, arrows = false, r }) {
    const w = h * (r || ratio(items[0].path));
    items.forEach((it, i) => {
      s.addImage({ path: it.path, x, y, w, h, altText: it.alt || it.cap });
      s.addShape(pres.shapes.RECTANGLE, { x, y, w, h, fill: { type: 'none' }, line: { color: C.beige, width: 0.75 } });
      const cw = w + Math.min(gap, 0.6) - 0.05;
      T(s, it.cap, { x: x - (cw - w) / 2, y: y + h + 0.1, w: cw, h: 0.3, fontSize: 12, bold: true, align: 'center' }, '화면 캡션');
      if (it.sub) T(s, it.sub, { x: x - (cw - w) / 2, y: y + h + 0.42, w: cw, h: 0.28, fontSize: 10.5, color: C.muted, align: 'center' }, '화면 설명');
      if (arrows && i < items.length - 1) T(s, '→', { x: x + w, y: y + h / 2 - 0.2, w: gap, h: 0.4, fontSize: 16, color: C.muted, align: 'center' });
      x += w + gap;
    });
    return x - gap;
  }
  // 설명 목록: 굵은 제목 + 회색 설명 (번호 원 없음)
  function notes(s, items, { x, y, w, gap }) {
    items.forEach((it, i) => {
      const yy = y + i * gap;
      T(s, it[0], { x, y: yy, w, h: 0.36, fontSize: 14, bold: true }, '설명 제목');
      T(s, it[1], { x, y: yy + 0.4, w, h: gap - 0.5, fontSize: 12, color: C.muted, valign: 'top' }, '설명');
    });
  }
  // 핵심 한 줄: 배경색 없이 왼쪽 얇은 세로선 + 굵은 글씨(시선을 뺏지 않는 요약). [[ ]] 부분만 빨간 굵은 글씨
  function key(s, t, { x, y, w, h = 0.5, size = 13 }) {
    s.addShape(pres.shapes.RECTANGLE, { x, y: y + 0.08, w: 0.05, h: h - 0.16, fill: { color: C.dark }, line: { color: C.dark, width: 0 } });
    T(s, t, { x: x + 0.2, y, w: w - 0.2, h, fontSize: size, bold: true, color: C.text }, '핵심 문장 요약');
  }
  // 간지: 영역 시작 장. 어두운 배경 + 영역 이름 + 담은 장 목록
  function divider({ name, desc, items }) {
    const s = pres.addSlide(); s.background = { color: C.dark };
    T(s, name, { x: 0.9, y: 2.2, w: 11.5, h: 0.9, fontSize: 34, bold: true, color: C.white });
    T(s, desc, { x: 0.9, y: 3.15, w: 11.5, h: 0.45, fontSize: 15, color: C.tan });
    s.addShape(pres.shapes.LINE, { x: 0.9, y: 3.85, w: 11.5, h: 0, line: { color: C.muted, width: 0.75 } });
    (items || []).forEach((it, i) => T(s, it, { x: 0.9, y: 4.05 + i * 0.38, w: 11.5, h: 0.34, fontSize: 13, color: C.muted3 }, '간지 목록'));
    pages.push(s); return s;
  }
  function cap(s, { path, x = X0, y, w, alt, caption }) {
    const h = w / ratio(path);
    s.addImage({ path, x, y, w, h, altText: alt });
    s.addShape(pres.shapes.RECTANGLE, { x, y, w, h, fill: { type: 'none' }, line: { color: C.beige, width: 0.75 } });
    if (caption) T(s, caption, { x, y: y + h + 0.1, w, h: 0.3, fontSize: 11, color: C.muted }, '캡처 캡션');
    return y + h;
  }
  const cell = (t, o = {}) => ({ text: t, options: Object.assign({ fontFace: F, fontSize: 12, color: C.text, valign: 'middle', margin: [0.05, 0.12, 0.05, 0.12] }, o) });
  // 표: head 있으면 머리행(tan), 첫 열 굵게. 구분 칸이 '신규 개발' 등이면 badge-bg 배경
  function table(s, head, rows, { x = X0, y, colW, rowH = 0.48, headH = 0.42, firstBold = true, size = 12, align }) {
    const data = (head ? [head.map(t => cell(t, { bold: true, fill: { color: C.tan }, fontSize: size }))] : [])
      .concat(rows.map(r => r.map((t, j) => cell(t, { bold: firstBold && j === 0, fontSize: size, fill: firstBold && j === 0 && !head ? { color: C.soft } : undefined }))));
    const rh = data.map((_, i) => (head && i === 0) ? headH : (Array.isArray(rowH) ? rowH[i - (head ? 1 : 0)] : rowH));
    data.forEach((r, i) => r.forEach((c, j) => {
      const raw = c.text, isHead = head && i === 0;
      const f = fit(strip(raw), { w: colW[j] - 0.24, h: rh[i] - 0.1, size: c.options.fontSize, bold: !!c.options.bold, name: `표 ${i + 1}행 ${j + 1}열` });
      if (f.charSpacing) c.options.charSpacing = f.charSpacing;
      c.text = rich(raw, f.text, f.charSpacing ? { charSpacing: f.charSpacing } : null);
      if (!isHead && NEW_CELL.indexOf(strip(raw)) >= 0) { c.options.fill = { color: C.newCell }; c.options.bold = true; }
      if (align && align[j]) c.options.align = align[j];   // 숫자 열은 'right'
    }));
    s.addTable(data, { x, y, w: colW.reduce((a, v) => a + v, 0), colW, rowH: rh, border: { type: 'solid', pt: 0.75, color: C.beige }, objectName: '표' });
    return y + rh.reduce((a, v) => a + v, 0);
  }
  // 핵심 수치 칸: 큰 숫자 + 설명. hi: 숫자를 빨강으로 강조할 칸 번호
  function stats(s, items, { y, h = 1.25, hi }) {
    const n = items.length, gap = 0.2, w = (W0 - gap * (n - 1)) / n;
    items.forEach((it, i) => {
      const x = X0 + i * (w + gap), on = i === hi;
      s.addShape(pres.shapes.RECTANGLE, { x, y, w, h, fill: { color: C.soft }, line: { color: C.soft, width: 1 } });
      T(s, it[0], { x: x + 0.25, y: y + 0.15, w: w - 0.5, h: 0.6, fontSize: 28, bold: true, color: on ? C.red : C.text }, '핵심 수치');
      T(s, it[1], { x: x + 0.25, y: y + 0.78, w: w - 0.5, h: 0.32, fontSize: 12, color: C.muted }, '수치 설명');
    });
  }
  // 쪽 번호 = PowerPoint 슬라이드 번호(표지 포함). 피드백의 'n p'와 화면 번호가 어긋나지 않게 한다
  async function save(f) {
    const off = hasCover ? 1 : 0, total = pages.length + off;
    pages.forEach((s, i) => T(s, `${i + 1 + off} / ${total}`, { x: 11.73, y: 7.0, w: 1.0, h: 0.28, fontSize: 9, color: C.muted3, align: 'right' }));
    return pres.writeFile({ fileName: f });
  }
  return { pres, T, cover, slide, divider, count: () => pages.length + (hasCover ? 1 : 0), phones, notes, key, cap, table, stats, save, C };
}
module.exports = { deck, X0, W0 };
```

## 부록 E. 흐름도 부품 (4-C, v3.8)

`slim.js`의 `deck()` 결과(`pres`, `T`, `C`)를 받은 생성 스크립트 안에 그대로 넣어 쓴다. 좌표 · 색 · 글자 크기는 고치지 않고 `N()` · `edge()` 인자로만 내용을 넣는다.

```js
const { pres, T, C } = D;   // D = deck('제목')
// ---------- 흐름도 부품 ----------
const NW = 2.1, DH = 0.85, PH = 0.66, FS = 11;
const CX = [0, 1, 2, 3, 4].map(i => 0.6 + NW / 2 + i * ((12.13 - NW) / 4));   // 5열 중심 x, 좌우 끝 0.6 · 12.73
const g = (a, b) => (CX[a] + CX[b]) / 2;
function node(s, n) {
  const w = n.w || NW, h = n.h || (n.k === 'dec' ? DH : PH);
  const x = n.cx - w / 2, y = n.cy - h / 2;
  Object.assign(n, { w, h, x, y });
  const S = pres.shapes;
  if (n.k === 'end') s.addShape(S.ROUNDED_RECTANGLE, { x, y, w, h, rectRadius: 0.12, fill: { color: C.dark }, line: { color: C.dark, width: 0.75 } });
  if (n.k === 'proc') s.addShape(S.RECTANGLE, { x, y, w, h, fill: { color: C.soft }, line: { color: C.soft, width: 0.75 } });
  if (n.k === 'dec') s.addShape(S.DIAMOND, { x, y, w, h, fill: { color: C.white }, line: { color: C.dark, width: 1 } });
  if (n.k === 'scr') s.addShape(S.RECTANGLE, { x, y, w, h, fill: { color: C.white }, line: { color: C.muted3, width: 1 } });
  const inset = n.k === 'dec' ? { w: w * 0.66, h: h * 0.72 } : { w: w - 0.16, h: h - 0.06 };
  T(s, n.t, { x: n.cx - inset.w / 2, y: n.cy - inset.h / 2, w: inset.w, h: inset.h, fontSize: n.fs || FS,
    bold: n.k === 'dec' || n.k === 'end', color: n.k === 'end' ? C.white : C.text, align: 'center' }, '흐름 ' + n.k);
  return n;
}
const anchor = (n, side) => !n.w ? n : ({ r: { x: n.x + n.w, y: n.cy }, l: { x: n.x, y: n.cy }, t: { x: n.cx, y: n.y }, b: { x: n.cx, y: n.y + n.h } })[side];
function seg(s, a, b, arrow) {
  const x = Math.min(a.x, b.x), y = Math.min(a.y, b.y), w = Math.abs(b.x - a.x), h = Math.abs(b.y - a.y);
  if (w < 0.001 && h < 0.001) return;
  s.addShape(pres.shapes.LINE, { x, y, w, h, flipH: b.x < a.x, flipV: b.y < a.y, line: { color: C.muted, width: 1, endArrowType: arrow ? 'triangle' : undefined } });
}
function edge(s, a, sa, b, sb, { lab, via, lx = 0, ly = 0, lw = 0.7 } = {}) {
  const p1 = anchor(a, sa), p2 = anchor(b, sb), H = v => v === 'r' || v === 'l';
  let pts;
  if (via) pts = [p1, ...via, p2];
  else if (H(sa) && (H(sb) || !b.w)) pts = Math.abs(p1.y - p2.y) < 0.01 ? [p1, p2] : [p1, { x: (p1.x + p2.x) / 2, y: p1.y }, { x: (p1.x + p2.x) / 2, y: p2.y }, p2];
  else if (!H(sa) && !H(sb)) pts = Math.abs(p1.x - p2.x) < 0.01 ? [p1, p2] : [p1, { x: p1.x, y: (p1.y + p2.y) / 2 }, { x: p2.x, y: (p1.y + p2.y) / 2 }, p2];
  else if (H(sa)) pts = [p1, { x: p2.x, y: p1.y }, p2];
  else pts = [p1, { x: p1.x, y: p2.y }, p2];
  for (let i = 0; i < pts.length - 1; i++) seg(s, pts[i], pts[i + 1], i === pts.length - 2);
  if (lab) {
    const o = { r: [0.05, -0.27], l: [-lw - 0.05, -0.27], b: [0.07, 0.02], t: [0.07, -0.27] }[sa];
    T(s, lab, { x: p1.x + o[0] + lx, y: p1.y + o[1] + ly, w: lw, h: 0.25, fontSize: 10, bold: true, color: C.muted, align: sa === 'l' ? 'right' : 'left' }, '분기 이름');
  }
}
// 범례: 오른쪽 끝을 본문 끝선(12.73)에 맞춤
function legend(s) {
  const items = [['end', '시작 · 끝', 0.75], ['proc', '앱 · 서버 · B.O 처리', 1.55], ['dec', '판단', 0.4], ['scr', '손님 · 운영자 안내', 1.35]];
  const total = items.reduce((a, it) => a + 0.38 + it[2], 0) + 0.2 * (items.length - 1);
  let x = 12.73 - total;
  const S = pres.shapes;
  items.forEach(([k, t, tw]) => {
    const o = { x, y: 0.45, w: 0.3, h: 0.18 };
    if (k === 'end') s.addShape(S.ROUNDED_RECTANGLE, Object.assign(o, { rectRadius: 0.05, fill: { color: C.dark }, line: { color: C.dark, width: 0.75 } }));
    if (k === 'proc') s.addShape(S.RECTANGLE, Object.assign(o, { fill: { color: C.soft }, line: { color: C.soft, width: 0.75 } }));
    if (k === 'dec') s.addShape(S.DIAMOND, Object.assign(o, { fill: { color: C.white }, line: { color: C.dark, width: 1 } }));
    if (k === 'scr') s.addShape(S.RECTANGLE, Object.assign(o, { fill: { color: C.white }, line: { color: C.muted3, width: 1 } }));
    T(s, t, { x: x + 0.38, y: 0.42, w: tw, h: 0.24, fontSize: 10, color: C.muted }, '범례');
    x += 0.38 + tw + 0.2;
  });
}
const N = (s, k, c, cy, t, o = {}) => node(s, Object.assign({ k, cx: CX[c], cy, t }, o));
const note = (s, t, o) => T(s, t, Object.assign({ h: 0.3, fontSize: 11, color: C.muted, valign: 'top' }, o), '보조 설명');   // 항목이 여럿이면 줄마다 '- '
```

# 간결 기획서형(기획서 · 화면 흐름 정의서 · 요구사항 정의서 · 통합본 · 흐름도 중심 중간 보고)

기준 덱: 「미니시즌 '최애 메뉴 부활 투표' 앱 이벤트 기획서 통합본 v0.2」(2026-10-20, 표지 포함 37장). 기능 보고형의 반복 컴포넌트를 걷어내고(사용자 지시: "반복 노출되는 우선순위 낮은 컴포넌트는 과감히 제거, 핵심 정책 · 기능 강조") 간지 · 화면 구조 장 · 빨간 강조 · 상태 전이 장을 쓴다. 공통 기준은 `references/design-common.md` · `references/writing.md` · `references/text-fit.md`를 따른다.

## 기능 보고형 대비 바꾼 점

| 항목 | 기능 보고형 | 간결 기획서형 | 이유 |
|---|---|---|---|
| 상단 흐름 헤더(오각형 · 쉐브론 단계 띠) | 매 장 | **없음** | 20장 넘는 덱에서 같은 띠가 반복돼 시선을 뺏고 정보가 늘지 않음 |
| 장 구분 칩(기능 소개 / 화면 상세) | 매 장 | **없음**, 왼쪽 위 작은 영역 이름(11pt muted)으로 대체 | 영역만 알면 충분 |
| 설명 순번 원 | 있음 | **없음**, 굵은 제목 + 회색 설명 | 순서 없는 설명에 번호를 붙이지 않음 |
| 하단 정보줄 | 날짜 · 문서 종류 · 쪽 번호 | **쪽 번호만**(9pt muted3) | 날짜는 표지에만 |
| 강조 | 흐름 박스 · 단계 카드의 노랑 1칸 | **배경색 없음.** 장당 핵심 한 줄 + 본문 속 정책 문구 빨강 + 「신규 개발」 칸 배지(`references/writing.md` 「강조」) | 노랑 띠는 시선을 뺏어 본문보다 먼저 읽힘 |
| 영역 구분 | 흐름 헤더 | **간지 1장**(어두운 배경 + 영역 이름 + 담은 장 번호 · 제목 목록) | 반복 띠 대신 영역 시작에서 한 번만 |
| 화면 구조 | 없음 | **개요 안에 화면 구조 장**(전체 길이 캡처 + 영역 번호 + 구분 표) | 개발자가 화면 전체와 재사용/신규 범위를 먼저 파악 |
| 화면 수 | 3개 고정 | 1~6개 | 상태 · 분기 비교에 4~6화면이 필요 |

- 본문 시작 높이는 기능 보고형과 같다(y 1.95). 공간이 늘어난 것이 아니라 시각 잡음이 줄어든 것이다.

## 정렬 끝선

기준: 「신규 오픈 매장 프로모션 고도화 중간 보고」 개요 장 사용자 수정본.

- 한 장 안의 표 · 흐름 박스 줄 · 핵심 한 줄 · 캡처는 왼쪽 시작 0.6과 오른쪽 끝 12.73을 같게 맞춘다.
- 칸 몇 개짜리 줄은 첫 칸 왼쪽 = 0.6, 끝 칸 오른쪽 = 12.73으로 두고 사이 간격을 균등하게 나눈다. 칸 시작 간격 = (12.13 − 칸 폭) / (칸 수 − 1). 4칸 · 폭 2.56이면 시작 간격 3.19 · 칸 사이 0.63.
- 범례 · 보조 설명 · 오른쪽 열 글상자도 오른쪽 끝이 12.73을 넘지 않게 오른쪽 기준으로 계산해 둔다. 왼쪽에서 폭을 더해 가다 끝선을 넘기는 배치는 금지.
- 표의 열 폭 합 = 본문 폭(12.13)으로 맞추고, 정보가 적은 열(진행 현황 등)은 빼서 남은 열에 폭을 나눈다.

## 부품(`slim.js`)

| 함수 | 용도 | 규칙 |
|---|---|---|
| `phones(s, items, {x, y, h, gap, arrows})` | 휴대폰 화면 나열 + 캡션(12pt Bold) + 설명 1줄(10.5pt) | 같은 줄 화면은 첫 이미지 비율로 폭 통일. **비율이 다른 이미지(팝업 크롭 등)는 높이를 같게 패딩한 뒤 넣는다** |
| `notes(s, items, {x, y, w, gap})` | 굵은 제목(14pt) + 회색 설명(12pt) 목록 | 제목 20자 이내 1줄, 설명 2줄 이내 |
| `key(s, text, {x, y, w, h, size})` | 핵심 한 줄: 배경 없음, 왼쪽 다크 세로선 0.05in + 굵은 글씨 | **장당 1개 이하.** 표 바로 아래 0.2in 이상 띄움 |
| `stats(s, items, {y, hi})` | 핵심 수치 칸(soft 배경, 28pt 숫자 + 12pt 설명) | 개요 장 전용, `hi` 칸은 숫자만 빨강(`references/writing.md` 「강조」) |
| `table(s, head, rows, {x, y, colW, rowH, headH, size, align})` | 머리행 표(head) 또는 라벨 표(head=null, 첫 열 soft) | 칸 줄바꿈은 `\n`으로 직접, 12pt(밀도 높으면 10.5~11pt). 칸 글자가 정확히 「신규 개발」이면 자동으로 badge-bg 배경 + 굵게(`references/writing.md` 「강조」). `rowH` 배열은 머리행을 뺀 본문 행 수만큼. 숫자 열은 `align` 'right' |
| `[[문구]]` 표시 | 빨간 굵은 글씨 | 쓰는 곳 · 개수는 `references/writing.md` 「강조」 |
| `divider({name, desc})` | 간지(dark 배경, 34pt 영역 이름 + 15pt 설명 + 구분선) | 담은 장 목록은 덱 끝에서 채움(아래 「장 번호 자동 계산」) |
| `count()` | 지금까지 만든 장 수(표지 포함) = 방금 만든 장의 번호 | 목차 · 간지 · 체크리스트의 장 번호 자동 계산용 |
| `cap(s, {path, x, y, w, caption})` | B.O · 표 캡처 | 캡처 폭 대비 글자가 읽히도록 원본을 좁은 뷰포트(760px 안팎)에서 다시 캡처 |
| `kit(title)`(`kit.js`) | `sec` · `sl` · `tx` · `nl` · `tb` · `key` · `img` · `finish` | `tb`는 칸 폭 기준으로 직접 줄을 나누고 행 높이를 계산해, 표가 6.85를 넘으면 생성을 멈춘다. `MGC_FIT=warn`으로 돌리면 넘침을 한 번에 모아 본다 |
| 흐름도 부품(`flow_parts.js`) | 흐름도 상자 · 연결선 · 범례 · 보조 설명 | `references/flowchart.md` |

- 폭 검산: 화면 n개 폭 합 = n × h × 비율 + (n−1) × gap ≤ 12.13. 6화면을 h 4.2로 두면 넘친다(4.0으로).
- 높이 검산: 화면 y + h + 0.72(캡션 · 설명) ≤ 6.9. 표 바로 아래 캡처 · 강조는 0.2in 이상 띄운다.
- 화면 오른쪽 설명(`notes`)의 x는 마지막 화면 오른쪽 끝 + 0.4 이상. 화면을 빼서 1개만 남으면 오른쪽 표를 화면 쪽으로 당겨 빈 폭을 없앤다.
- **상태 전이 장**: 캡처는 반드시 시간 순서(왼쪽 → 오른쪽)로 놓고, 열마다 같은 위쪽 기준선에 맞춘다. 캡처 높이가 다르면 아래로 남는 공간을 비워 두고 표의 열과 1:1로 맞춘다. 상태 이름은 캡처 위 캡션과 표 머리행에 같은 문구로 쓴다. 상태 위치가 흩어져 "어떤 구분인지 모르겠다"는 피드백을 막기 위한 배치다.
- **화면 구조 장 영역 표시**: 캡처 위 영역마다 doc-accent-gold 1.25pt 테두리(안쪽 0.02in) + 왼쪽 바깥(x − 0.29) 지름 0.24 골드 원에 흰 번호 10pt Bold. 표 첫 열 번호와 1:1로 맞춘다. 영역은 빈틈 없이 위에서 아래 순서로 나누고, 표 '구분'은 재사용 · 확장 · 신규 개발 · 이미지 · B.O 등록 중 하나. 현행 모듈을 그대로 쓰는 영역(헤더 등)은 동작 설명을 붙이지 않고 '재사용'으로만 둔다.
- 화면 구조 표 오른쪽 끝(x + 열 폭 합)이 12.73을 넘지 않고, 3단 마지막 단 오른쪽 끝 + 0.1 ≤ 표 x 인지 검산한다(첫 시도에서 0.02in 겹친 사례).

## 제작 절차

1. **화면 캡처**: 프로토타입에서 Playwright 2배 해상도로 다시 캡처한다(이전 덱 이미지 재사용 금지: 문구 · 쿠폰명이 바뀌어 있을 수 있음). 팝업은 요소 크롭(여백 12px) 후 높이를 맞춰 패딩한다.
   - **전체 길이 화면**(화면 구조 장): 스크롤 영역을 (높이 − 40px)씩 내리며 캡처해 스크롤 영역 부분만 이어 붙이고, 맨 위 헤더와 맨 아래 하단 고정 버튼은 첫 캡처에서 잘라 붙인다. 영역 좌표는 같은 때 DOM `getBoundingClientRect()`로 받아 JSON에 저장해 번호 위치에 쓴다. 단 나누는 지점은 섹션 경계(다음 섹션 top)로 잡아 앞 섹션 배경이 다음 단 맨 위에 남지 않게 한다. 아주 긴 영역(유의사항 등)은 잘라 쓰고 점선으로 생략을 표시한다.
   - **상태 화면은 사용자가 처음 보는 기본 화면으로 캡처한다.** 예: 종료 상태는 진입 직후 상단 종료 딤 화면(scrollTop 0)이 기본이고, 아래 랭킹은 사용자가 스크롤해서 본다. 캡처 설명도 "상단 종료 딤 · 랭킹은 스크롤"처럼 기본 화면 기준으로 쓴다.
2. **장 순서**(장마다 위 배치 중 하나를 고른다)
   - 기획서 · 통합본: 표지 → 목차(읽는 순서) → [간지 개요] 핵심 정책 · 고객 흐름 · **화면 구조(상세 · 바텀시트)** · 재사용/신규 · 용어 → [간지] 기능 영역들(고객이 겪는 순서) → [간지] 연동 · 랭킹 → [간지] 운영 · 개발 범위(B.O · 데이터 · 개발 영역 · 놓치기 쉬운 점) → [간지] 부록.
   - 흐름도 중심 중간 보고: 표지 → 개요(단계 표 + 단계 연결 박스 줄 + 핵심 한 줄) → [간지] 1단계 → 흐름도 장 → [간지] 2단계 → 흐름도 장 … 단계마다 간지 1장. 간지 설명 줄은 "개발 요청 n번 · 적용 시점, 한 줄 요약", 목록에는 담은 장 번호 · 제목. 목차 장은 장이 12장 이하면 생략한다.
   - 개발 연동 통합본: `references/integration-doc.md` 「장 구성」.
3. **기획서에 기본으로 넣지 않는 장**(사용자가 요청할 때만): 서버 저장 데이터 · API, 예외 처리 · 안내 문구, 태스크별 공수(내부 참고값은 벤더 공유 금지), 남은 결정 항목, 전체 일정 · 함께 보는 자료. 확인이 필요한 항목은 덱 대신 답변에서 따로 알린다.
4. **프로토타입이 키값이다.** 덱의 따옴표 안 화면 문구("...")는 프로토타입 문구 원본(MSG 등)과 자동 대조해 불일치를 0으로 맞춘다. 현행 화면 모듈에 없는 UI(예: 출석 경품 칸에 '기간 부족' 사유 문구)를 기획서나 프로토타입에 임의로 더하지 않는다. 프로토타입을 고치면 검증 → 재캡처 → 덱 재생성 → PRD 순서로 동기화한다.
5. **생성 · 검수**: `node 생성스크립트.js out.pptx` → `references/qa-checklist.md`. 렌더 후 장 제목을 추출해 목차 · 간지 · 체크리스트 장 번호와 대조한다.
6. 사용자가 PPT를 직접 고쳐 보내면 `references/edit-user-pptx.md`로 넘어간다.
7. 사용자에게 넘기기 전에 `references/final-deliverable.md` 점검을 모두 통과시킨다.

## 장 번호 자동 계산 · 화면 구조 영역 표시(생성 스크립트 쪽)

장 번호는 손으로 적지 않는다. `sec(name, desc, look)`로 간지를 만들고 일반 장은 `sl({id, ...})`로 만들어 `count()`로 번호를 모은 뒤, 덱 끝에서 간지 목록 · 목차 표 · 체크리스트 관련 장 번호를 채운다. 장을 넣고 빼도 번호가 저절로 맞는다.

```js
const D = deck('제목'); const { cover, slide, divider, count, table, key, T } = D;
const SECS = []; let CUR = null; const PG = {};
function sec(name, desc, look) { const d = divider({ name, desc }); CUR = { name, desc, look, div: d, start: count(), titles: [] }; SECS.push(CUR); }
function sl(o) { const x = slide(o); if (CUR) CUR.titles.push([count(), o.title]); if (o.id) PG[o.id] = count(); return x; }
// 화면 구조: 캡처(x, y, 375px 폭, 배율 k in/px) 위 영역 [번호, top px, bottom px]
function regions(s, x, y, k, regs) {
  regs.forEach(([n, t, b]) => {
    s.addShape(D.pres.shapes.RECTANGLE, { x: x + 0.02, y: y + t * k + 0.01, w: 375 * k - 0.04, h: (b - t) * k - 0.02, fill: { type: 'none' }, line: { color: 'D98C1F', width: 1.25 } });
    s.addShape(D.pres.shapes.OVAL, { x: x - 0.29, y: y + t * k + 0.02, w: 0.24, h: 0.24, fill: { color: 'D98C1F' }, line: { color: 'D98C1F', width: 0 } });
    T(s, String(n), { x: x - 0.29, y: y + t * k + 0.02, w: 0.24, h: 0.24, fontSize: 10, bold: true, color: 'FFFFFF', align: 'center' }, '화면안 번호');
  });
}
// ... 표지 → const TOC = sl({...목차}) → sec('개요', ...) → sl({ id: 'struct1', ... }) ...
// 덱 끝: 간지 목록 · 목차 채우기
SECS.forEach(x => {
  x.end = x.titles.length ? x.titles[x.titles.length - 1][0] : x.start;
  x.titles.forEach((t, i) => T(x.div, `${t[0]}    ${t[1]}`, { x: 0.9, y: 4.05 + i * 0.38, w: 11.5, h: 0.34, fontSize: 13, color: 'A6968A' }, '간지 목록'));
});
table(TOC, ['영역', '장', '담은 내용', '개발 관점에서 볼 것'], SECS.map(x => [x.name, `${x.start}~${x.end}`, x.desc, x.look]), { y: 1.95, colW: [2.2, 0.9, 5.23, 3.8], rowH: 0.48, size: 11.5 });
```

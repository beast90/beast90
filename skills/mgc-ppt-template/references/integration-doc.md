# 개발 연동 통합본 · API 연동 정의서

기준 덱: 「앱카드 연동 통합본」(v0.12 표지 포함 81장 → v0.25 표지 포함 88장). 개발사 · 연동사 · 결제대행사가 함께 보는 연동 문서다. 기획서(`references/genre-slim-spec.md` 「제작 절차」 3번 기본 제외 항목)와 달리 API · 처리 흐름 · 예외 · 공수 범위 장을 넣는다. 골격 · 부품은 간결 기획서형을 따른다.

## 장 구성

표지 → 읽는 순서 → [간지] 개요 → 확정 정책 → 화면 명세 → 연동 구조 · API → 처리 흐름 → 예외 처리 → 결제대행사 · 정산 → 개발 범위 · 운영 → 확인 필요 → 부록(문서 간 불일치 · 용어). 간지 목록은 2열 12개까지(`kit.js` `finish`).

## 개요 필수 장

- 결론 · 핵심 수치(`stats`) + 정책 라벨 표 + 요약 연동 구조 도식.
- 독자별 먼저 볼 장: 독자를 맡은 범위로 나누고, 「먼저 볼 장」 칸에 영역 이름과 장 범위를 같이 쓴다(예: "정책(10~19) · 화면(20~26)"). 먼저 볼 장은 장 하나에 「- 」 한 줄. 범위 숫자는 덱 끝에서 다시 계산한다.
- 앱 구조(아키텍처) 도식: 새 연동의 데이터 흐름에 순서 번호 원(지름 0.26in, doc-bg-800, 흰 숫자 10pt)을 붙이고, 아래 1줄 "※ 1~n은 ○○ 데이터 흐름 순서, 번호 없는 선은 현행 흐름". API 번호(①)와 겹치지 않게 흐름 번호는 원 안 숫자로 쓴다.
- 구성 요소 표: 구성 요소 | 쓰는 흐름(로그인 · 결제 · 카드 관리) | 위치 | 하는 일 | 개발 주체 · 구분.

## 개발 주체 · 구분 값

- 주체와 구분을 함께 쓴다: "CJ ONS · 기존 수정", "CJ ONS · 신규 개발", "핏콜라보 · 제공", "카드사", "OnePG · 범위 확인". "CJ ONS(신규)"처럼 괄호로 줄인 표기는 쓰지 않는다.
- 정책 표의 개발 구분 열(상태 열 대신):
  - 현행 구조와 맞지 않으면 "[[신규 개발]](현행 1:1 구조와 다름)"
  - 현행 화면 · 기능에 요소만 더하면 "기존 수정(○○ 추가)"
  - 정해지지 않았으면 확인 태그(`references/writing.md` 「확인 태그」)
  - "적용" · "적용(구조 개선)" 같은 뜻이 흐린 값은 쓰지 않는다.

## 번호 체계 원본 장 · 출처 줄

- API · 단계에 번호(로그인 ① · 결제 ②)를 쓰면 번호 목록 장 1장을 원본으로 둔다(번호 | API | 호출 경로 | 서버 · 규격 | 역할). 그 장 핵심 문장에 "번호는 이 장이 원본"이라고 쓴다.
- 번호를 쓰는 다른 모든 장 하단(x 0.6, y 7.02, w 10.9, 9pt muted, 이름 "출처")에 "※ API 번호(로그인 ① · ② / 결제 ①~⑥ / 카드 관리 ①)는 N장 목록 기준"을 둔다(`add_source_line`).
- 본문에서는 번호만 쓰지 않고 이름과 함께 쓴다: "결제 ②"(×) → "결제 거래번호 발급 ②(requestTid.mv)"(○). 표의 번호 열 · 좁은 칸은 예외.

## 키(한글 이름) 표기

- 파라미터 · 응답 키는 처음부터 끝까지 "키(한글 이름)" 형식으로 쓴다(예: transNo(인증 거래번호), deviceType(기기 구분), payType(카드 구분)). 호출값 · 키값 · 식별값 표와 정책 표 모두 같다. 한글 이름은 아래 사전을 따른다.
- 호출값 표: 호출값 | 필수 | 설명 | 적용값. 적용값 칸은 값과 이유를 함께 쓴다(예: "N(Webview의 공통 웹 컴포넌트에서 호출)", "보내지 않음(고객이 인증 모듈에서 카드사 선택)").
- 키값 표: API(번호 / 이름 / 호출명 3줄) | 역할 | 보내는 값 | 받는 값. 보내는 값 · 받는 값은 의미 묶음마다 「- 」 줄. 한 장에 안 들어가면 장을 나눈다(`references/text-fit.md` 「넘칠 때 고치는 순서」).
- **상태 · 구분 값의 기준 시점**: "기존 카드 · 새 카드"처럼 상태로 나뉘는 값은 앱 처리 흐름에서 언제 생기고 어느 화면 요소에 보이는지 각주로 정의한다(예: "기존 카드는 앱카드 로그인 인증 · 이전 결제 · 카드관리 페이지 등록으로 이미 등록된 카드, 주문하기 진입 때 계정 목록 조회 ①로 받아 화면 2 · 3의 1a에 보임").

## 처리 구조 장

- 이동 · 복귀처럼 여러 단계가 이어지는 주제는 왼쪽 설명(w 6.0) + 오른쪽 세로 구조 도식(x 7.0, w 5.73, 상자 높이 0.6, 상자 사이 0.23 화살표, 플랫폼 갈래는 2칸 폭 2.75)으로 그린다.
- 업체 색: 핏콜라보 partner-pink + error-red 테두리, Webview doc-surface-soft, Native doc-bg-800, 외부 흰 바탕(`references/design-common.md` 「컬러 토큰」).

## 쓰는 내용의 범위

- **채택한 방식만 쓴다**: 쓰지 않는 방식과의 비교표(예: 앱 직접 호출 vs 공통 웹 컴포넌트)는 만들지 않는다. 채택한 방식을 항목별(요청 → 표시 → 결과 수신 → 서버 확정 → 복귀 → Native 작업)로 자세히 쓴다.
- **현행 비교 열은 꼭 필요할 때만**: 범위 설명 장(예: 카드 관리)은 새 기능의 범위 · 기능 · 메가MGC커피 개발 몫만 쓴다. 현행 비교는 "현행과의 차이" 장 하나에 모은다.
- 쓰지 않기로 한 기능 · API 제거 규칙은 `references/final-deliverable.md` 「결정 과정 미노출」.
- **내부 판단 장 구분**: 정책 기준 · 법무 확인 장은 내부 자료다. 개발사 · 연동사에 보낼 때는 빼거나 정제본을 따로 만든다.

## 흐름도 · 송수신 이미지

- 이미지 위에 덧그리지 않는다. 원본 정의서 장을 먼저 고친 뒤 150dpi로 렌더해 같은 비율로 자르고, 덱 · docx 그림은 위치 · 크기를 두고 이미지만 바꾼다(`replace_picture`).
- 자르기 비율(흐름도 세로 0.235~0.865, 송수신 0.235~0.93)은 이관 문서에 남긴다.
- 단계를 빼면 번호를 다시 매기고, 장 제목의 단계 수("16단계")와 단계표를 같이 고친다.

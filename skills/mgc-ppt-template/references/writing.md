# 문구 · 기호 · 강조 규칙(모든 장르)

기준 서식: 「앱카드 연동 통합본 v0.25」 사용자 수정 4장. 덱 · 정의서 · docx에 같이 적용한다.

## 문체

| 위치 | 문체 | 규칙 |
|---|---|---|
| 슬라이드 제목(최상단) | 개조식 「토픽: 핵심 서술」 | 토픽은 그 장이 다루는 대상(「결제 전 체크」), 서술은 결론을 명사 · 개조식으로 끝냄(「결제 전 체크: 화면별 체크 통과 뒤에만 결제 거래번호 요청」). 한 줄 안(`references/text-fit.md` 「폭 추정 · 보정 값」). 전체를 본문색(2E241D)으로, 부분 색 · [[ ]] 없음 |
| 핵심 문장(기능 보고형 목적 문구 포함) · 핵심 한 줄 | 서술형 | 장의 결론을 읽는 사람에게 말하는 한 문장, 「~합니다」로 끝냄. 핵심 문장은 끝 온점을 찍고, 핵심 한 줄은 찍지 않음. 두 문장이 필요하면 쉼표로 이어 한 문장으로 |
| 표 칸 · 설명 · 본문 상자 · ※ 각주 · 출처 줄 · 도식 상자 문단 | 개조식 | 끝맺음 「~함 · ~음 · ~됨」. 「X입니다」 → 「X」, 「엽니다」 → 「열어 줌」, 「만듭니다」 → 「만듦」(어색한 「엶」 금지). 끝 온점 없음 |

- 개조식으로 바꿔도 뜻이 같아야 한다. 주어 · 목적어를 지우지 않는다(「승인 취소」 (×) → 「메가MGC커피 서버가 승인 취소 ⑤ 호출」 (○)).
- 고객 화면 문구(따옴표 안, 그대로 보여 줄 문구)는 문체를 바꾸지 않는다.

## 문장 명확성

- 제3자가 처음 읽어도 이해되게 모든 문장 · 항목에 누가(주어) 무엇을(목적어)을 쓴다: 「토큰 서버 보관」 (×) → 「메가MGC커피 서버가 로그인 ① 응답으로 받아 보관함」 (○).
- 「적용」 같은 상태 단어만 남기지 않고 뜻을 쓴다(「적용」 → 「정책 확정」, 「오감」 → 「송·수신」). 조각 문장은 술어까지 완성한다.
- 같은 사실을 장끼리 다르게 쓰지 않는다.
- 표의 행 이름은 상태가 아니라 토픽으로 쓴다(「확인 필요 1」 → 「사전 작업」, 「확인 필요 2」 → 「데이터 저장」).
- 한 문장에 주어가 다른 두 내용이 나란히 있으면 주어 앞에 ①②를 붙인다(「①인증 거래번호(transNo)는 로그인 인증, ②결제 거래번호(tid)는 결제 승인」). 3단계 이상 이어지는 순서(「A → B → C」)도 단계마다 ①②③을 붙인다. 단, API 번호(①~⑥)를 쓰는 칸 · 보내는 쪽 → 받는 쪽 경로에는 붙이지 않는다(번호 뜻이 겹침).

## 기호

의미 하나에 기호 하나.

| 기호 | 쓰는 곳 | 쓰지 않는 곳 |
|---|---|---|
| `- ` | 표 칸 · 설명 · 노트 상자의 정보 단위 글머리 | 빈 칸, 흐름도 상자 안 |
| `·`(앞뒤 공백) | 한 줄 안 나열(「주문번호 · tid」). 합성어는 붙여 씀(「송·수신」) | 글머리, 줄 머리 |
| `~` | 범위(「11~23」, 「2026.04~2028.03」) | 나열 |
| `—` | 빈 표 칸 1글자, **가운데 정렬** | 제목 · 영역 이름 · 간지 목록 · 문장 안 구분 |
| `: ` | 제목의 토픽 구분, docx 제목 · 그림 설명의 부연, 「값: 뜻」 | |
| `( )` | 영역 이름 · 간지 목록의 부연(「결제 정책(판단 · 경로)」) | |
| `•` · `–` | 쓰지 않음 | |

### 글머리 「- 」를 붙이는 기준(위에서부터 판정)

1. 표 열 단위: 설명 · 기준 · 처리 · 규칙 · 비고처럼 문장형 정보가 들어가는 열은 **정보가 1개여도** 모든 칸을 「- 」로 시작한다. 한 열에 글머리 칸이 하나라도 있으면 그 열 전체에 붙인다(`format_pass.include`).
2. 붙이지 않는 열: 이름 열(첫 열), 머리행, 값 · 코드 · 번호 · ● · 상태 · 개발 구분 · 위치 · 호출값 · 고객 화면 문구 열.
3. 표 밖 보조 설명 글상자 · 노트 상자: 서로 다른 정보가 2개 이상일 때만 정보마다 줄을 나누고 「- 」를 붙인다.
   - (×) "종료일은 최대 생성일 + 60일까지, 체크를 해제하면 즉시 미노출"
   - (○) "- 종료일은 최대 생성일 + 60일까지" / "- 체크를 해제하면 즉시 미노출"
4. 정보가 1개뿐인 상자, 한 정보가 폭 때문에 두 줄로 나뉜 칸(예: 'B.O · 메가오더' / '사전예약'), 흐름도 상자 안 글자에는 붙이지 않는다.

- 한 정보가 두 줄 이상이면 이어지는 줄은 「- 」 폭만큼 문단 들여쓰기(marL)로 맞춘다. 공백으로 들여쓰지 않는다(PowerPoint에서 줄이 다시 밀림).
- 칸 첫 글자가 빨강이어도 「- 」는 본문색으로 둔다.
- 글머리 줄은 끝 온점을 찍지 않는다.

## 강조

- 빨강은 기본 빨강 **FF0000** 하나만 쓴다(글자, 연동 도식 핏콜라보 상자 테두리). 면 채우기에는 쓰지 않는다. 이전 값(F53148 · D32F2F · docx C00000)이 남은 파일은 모두 FF0000으로 바꾼다.
- 굵은 빨강(`[[문구]]` 표시)은 현 시점 최종 정책 · 규칙 문구에만 쓴다(예: 하루 1번, 재투표 불가, 셔플은 재진입 · 새로고침 때만).
  - 정책 문구는 장당 3곳 이하. 확인 태그와 연동 도식의 업체 색 글자(아래)는 따로 센다.
  - 상태 값 · 개발 구분 값 · 표 머리 · 전체 문장 · 제목은 강조하지 않는다(예외: 개발 구분 열의 「신규 개발」).
  - `slim.js`의 모든 `T` · `notes` · `key` · `table` 칸에서 동작한다(`fit()`은 표시를 뺀 글자로 줄맞춤).
  - 개요 핵심 수치 칸(`stats`의 `hi`)은 숫자만 빨강.
- 연동 도식(아키텍처 · 처리 구조 · 요약 연동 구조) 안에서 핏콜라보 상자 이름과 핏콜라보 쪽 흐름 이름(「API 호출」 · 「인증 · 승인」 등)은 빨강 글자로 쓴다. 업체를 가리키는 색이라 정책 강조 개수에 넣지 않는다.
- 노랑 배경(badge-bg FDF9C9)은 개발 구분 값이 「신규 개발」인 칸에만 쓰고 그 칸을 굵게 한다(「CJ ONS · 신규 개발」 · 「신규 개발(현행 1:1 구조와 다름)」 포함). 행 전체 · 다른 칸에는 쓰지 않는다.
- 요약 띠(「라벨   내용」 한 줄 상자)는 라벨만 굵게, 내용은 보통 굵기.
- 기능 보고형 노랑 1곳 규칙은 `references/design-common.md` 「컬러 토큰」을 따른다.

## 확인 태그

정해지지 않은 항목은 누가 무엇을 해야 하는지 서술형 태그로 쓰고 빨간 굵은 글씨로 둔다(덱 · 정의서 · docx 공통).

- 형식: 「[주체 (↔ 상대) 내용 확인 필요]」, 법무는 「[법무팀 (내용) 검토 필요]」. 예: 「[핏콜라보 ↔ OnePG 연동 일정 검토 필요]」, 「[CJ ONS 현행 차감 시점 확인 필요]」.
- 「[확인필요(부서): 내용]」 · [미결] · "검토 중" 같은 다른 형식과 섞어 쓰지 않는다.
- 문장이 이미 판단 주체를 말하면 태그를 지운다(「적용 여부는 법무팀이 판단함」 뒤 태그 삭제).
- docx도 같은 서술형 태그를 빨간 굵은 글씨(FF0000)로 쓰고, 문서 앞 확실성 표기 설명도 같은 형식으로 고친다.
- 결정이 나면 그 문장의 태그를 지우고 정책 문구를 강조로 바꾼 뒤, 같은 사실을 다루는 모든 위치(핵심 한 줄 · 송수신 규칙 · 법무 목록 · docx 결론 · 이관 문서)에서 함께 지운다.

## 명칭 · 용어

- 같은 대상을 여러 이름으로 쓰지 않는다. 한 덱 안에서 하나로 통일한다.
  - 회사명은 「메가MGC커피」 전체 표기. 개발 · 운영사는 「CJ ONS」, 결제대행사 업체명은 「OnePG」(「CJ ONS(OnePG)」 · 「CJ PG」 금지).
  - 사람 지칭은 손님 또는 회원 중 하나. B.O 메뉴명('MY매장 등록 회원')은 그대로 둔다.
- 서비스 명칭은 작은따옴표로 쓴다: 'MY매장', '신규오픈'. 화면 캡처 속 UI 문구는 예외다.
- 오프라인 매체는 "오프라인 홍보물"로 쓴다.
- **줄인 말 금지**(공통 이해도를 떨어뜨림)
  - 번호 → 거래번호(인증 거래번호 · 결제 거래번호), 모듈 → 인증 모듈
  - 주체 없는 "서버" → 메가MGC커피 서버 / 핏콜라보 서버
  - PG → 결제대행사(정의에서만 "결제대행사(PG)"), 업체를 가리킬 때는 「OnePG」
  - 구성 요소로서의 "앱" → Native("카드사 앱", "메가MGC커피 앱", "앱 재배포"는 그대로)
  - "④ 미사용" → 기능 이름으로
  - 예외: 표 머리행의 좁은 열 이름(작업 매트릭스 "서버" 열)은 짧게 둔다.
- 개발 용어(API · 인코딩 · 리다이렉터 등)는 쓰지 않는다. 예외: 연동 문서는 API · 호출명 · 키를 쓰되 `references/integration-doc.md` 「키(한글 이름) 표기」를 지킨다.
- 과장 표현(혁신적인 · 스마트한 · 원활한 · 손쉽게 · Seamless 등)은 쓰지 않는다.

## 값 표기

- **예시값**: 화면안의 금액 · 인원 · 날짜는 "(예시)"로 표기한다. 정책값은 B.O 설정 기준으로 쓴다. 예: "B.O에서 정한 금액 할인 (화면은 1,000원 예시)".
- **기준점**: 기간 · 한도에는 기준점을 함께 쓴다. "최대 60일 연장"(×) → "최대 매장 생성일 + 60일"(○).
- **시점**: 오픈 전 · 당일 · 이후 같은 시점은 확정 정책과 대조한 뒤 쓴다.
- **단계 번호 = 개발 요청 번호**: 보고 덱의 단계 번호와 개발 요청 번호를 같게 쓴다. 이미 다른 번호로 요청이 나갔으면 다음 통합 메일에서 번호를 다시 매기고, 옛 번호 대응표는 메일에만 1회 넣는다(덱 · 정책 문서에는 새 번호만).
- 최종본에서 작업 이력 · 없어진 기능을 쓰지 않는 규칙은 `references/final-deliverable.md` 「작업 이력 금지」.

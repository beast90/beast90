# 스킬 유지보수 표준 (v1.0, 2026-10-26)

스킬을 고칠 때마다 이 절차를 따른다. 목적은 세 가지다.

- **찾기 쉬움**: 어떤 규칙이든 기준 위치 1곳에서 찾는다.
- **충돌 없음**: 같은 주제를 두 곳에서 다르게 말하지 않는다.
- **적게 읽음**: 작업마다 필요한 파일만 읽어 반영 시간을 줄인다.

## 1. 작업 판별

| 요청 | 할 일 |
|---|---|
| 새 지시 · 피드백을 스킬에 반영 | 3장 「규칙 반영 절차」 |
| 스킬이 길어 반영이 느림, 중복 · 모순 · 위계 점검 요청 | 4장 「구조 점검 · 재편 절차」 |
| 규칙 반영 5회마다, 또는 점검기 경고 10건 이상 | 4장을 이어서 수행 |
| 다른 작업 중 스킬에 없는 패턴을 발견 | 작업 답변 끝에 「스킬 반영 후보」로 알림. 사용자가 요청하면 3장 |

## 2. 표준 구조

```
<스킬>/
  SKILL.md          읽기 지도: 앞머리 · 전제 · 작업별 읽을 파일 · 분기 · 항상 적용 규칙(요약 + 기준 위치) · 우선순위 · 규칙 위치 지도 · 번들 파일
  references/*.md   규칙 본문. 한 작업에서 함께 읽는 묶음 단위로 나눈다
  scripts/          실행 코드. 문서에 코드를 길게 붙이지 않는다(사용 예 20줄 이내만 문서에)
  CHANGELOG.md      버전별 변경 내용. 규칙 본문에는 버전 꼬리표를 달지 않는다
  lint.json         점검기 설정: 기준값 · 금지어 · 주제별 기준 위치
```

- 크기 예산: SKILL.md 260줄 · 24KB 이하, 참조 파일 300줄 이하(넘으면 주제로 나눔).
- **한 주제 = 한 기준 위치.** 다른 파일은 규칙을 다시 쓰지 않고 「`references/x.md` 「제목」」으로 가리킨다. 검수표는 확인 문장만 두고 기준 위치를 가리킨다.
- 참조 표기는 파일 경로 + 「제목」을 쓴다. 숫자 · 영문을 이은 절 번호나 임의 코드명은 새로 만들지 않는다(뜻이 안 보이고 재편 때마다 바뀜).
- 장르 · 문서 유형 전용 값은 「공통」 파일에 두지 않는다. 공통 파일에 장르별 값이 필요하면 장르를 열로 둔 표 하나로 쓴다.
- 파일 하나의 절 순서: 원칙 → 규칙(무엇) → 절차(순서) → 예외 → 예시. 검수는 별도 파일.
- 자세한 분할 기준 · 템플릿: `references/structure-guide.md`.

## 3. 규칙 반영 절차

1. **규칙 문장으로 정리**: 사용자 지시를 「적용 범위 · 조건 → 행동 · 값 · 예외 · 근거(기준 덱 · 날짜)」로 적는다. 범위가 불분명하면 그 한 가지만 묻는다.
2. **기준 위치 찾기**: SKILL.md 「규칙 위치 지도」에서 주제의 기준 위치를 찾는다. 지도에 없는 새 주제면 가장 가까운 파일에 절을 만들고 지도에 한 줄 추가한다.
3. **같은 주제 기존 규칙 검색**: 핵심어 2~3개로 스킬 전체(`grep -rn`)를 검색해 같은 주제 문장을 모두 모은다. 판정은 아래 표.

| 판정 | 조건 | 처리 |
|---|---|---|
| 신규 | 같은 주제 문장 없음 | 기준 위치에 추가 |
| 대체 | 같은 대상 · 같은 범위인데 값 · 행동이 다름 | 기존 문장을 **고쳐 쓴다**. 옛 문장 · 옛 예시를 모든 위치에서 지운다 |
| 범위 분리 | 대상은 같으나 적용 상황이 다름(생성 vs 편집 등) | 상황을 열로 둔 표 하나로 합친다 |
| 충돌 | 어느 쪽이 맞는지 지시만으로 판단 불가 | 사용자에게 묻는다(5장 형식). 답을 받기 전에는 반영하지 않는다 |

4. **딸린 위치 동기화**: 같은 규칙을 가리키는 검수표 항목 · 예시 문장 · 사용 예 코드 · 스크립트 상수 · `lint.json` 기준값을 같이 고친다. 예시가 새 규칙을 어기지 않는지 확인한다(예: 개조식 규칙을 바꿨으면 예시 문장도 개조식).
5. **CHANGELOG.md**: 맨 위 버전에 1~3줄(무엇을 · 왜 · 대체한 옛 값). SKILL.md 제목 버전과 날짜를 올린다.
6. **점검**: `python3 scripts/skill_lint.py <스킬 폴더>` → 오류 0건. 경고는 새로 생긴 것만 처리한다.
7. **보고**: 「바뀐 규칙 · 기준 위치 · 같이 고친 위치 · 점검 결과」 표 1개. 규칙 원문을 다시 늘어놓지 않는다.

- 금지: 새 지시를 파일 끝이나 「추가 규칙」 절에 덧붙이기, 규칙 문장에 괄호 속 버전 · 개정 꼬리표 달기, 같은 규칙을 요약해 여러 곳에 다시 쓰기.

## 4. 구조 점검 · 재편 절차

1. **자동 점검**: `python3 scripts/skill_lint.py <스킬 폴더> --out 점검_전.md`. 처음이면 `references/lint-config-guide.md`로 `lint.json`을 만든다.
2. **수동 점검**: `references/review-checklist.md`의 위계 · 논리 · 중복 · 모순 항목을 읽으며 진단표(유형 · 위치 · 내용 · 처리안)를 만든다. 모순은 유형(값 · 범위 · 순서 · 예시-규칙 · 문서-코드 · 명칭)으로 나눈다.
3. **충돌 해소안**: 4-1의 기준으로 해소안을 정한다. 기준으로 정해지지 않는 항목만 사용자 결정 항목으로 묶는다.
4. **재편**: 2장 구조로 옮긴다. 원문 규칙을 하나도 버리지 않는다. 문서 속 긴 코드는 `scripts/`로 옮기고 실행해 확인한다.
5. **보존 대조**: 원문 문장 단위로 새 파일에 있는지 대조한다(`references/review-checklist.md` 「보존 대조」). 빠진 문장은 「옮김 · 의도적 대체 · 삭제(사유)」 중 하나로 분류해 보고한다.
6. **재점검**: `--out 점검_후.md` → 전후 수치(줄 수 · 바이트 · 오류 · 경고)를 표로 비교한다.

### 4-1. 충돌 해소 기준(위에서부터 적용)

1. 사용자가 가장 최근에 명시한 지시
2. 사용자가 직접 고쳐 준 산출물(기준본)의 실제 값
3. 적용 범위가 좁은 규칙(특정 장르 · 특정 장 · 특정 표) — 단 범위를 문장에 명시해 범위 분리로 처리
4. 실행 코드 · 실측값과 일치하는 쪽(문서가 코드와 다르면 문서를 코드에 맞추되, 코드가 더 오래된 판이면 사용자에게 확인)
5. 위 기준으로 정해지지 않으면 사용자 결정 항목

## 5. 사용자에게 묻는 형식

- 결정이 필요한 항목만 한 번에 묶는다. 항목마다: 충돌 위치 2곳 · 각 문장 · 추천안 1개(기본 적용 여부) · 다른 선택지.
- 작업은 막히지 않는 부분까지 끝내고, 추천안을 기본값으로 반영한 항목은 「기본 적용」으로 표시해 되돌리기 쉽게 한다.
